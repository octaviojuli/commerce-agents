# 旅游线路附件解析器

把供应商的行程附件（PDF、DOCX）整理成一份完整的线路内容：标题、封面卖点、行程亮点、附件中的价格信息（团费、另付费用、儿童价、单房差）、简要行程、逐日行程节点、费用包含与不含、购物与自费、单房差与退改、温馨提示。输出结构化 JSON，并渲染成手机和电脑都能看的详情页，另附给审核人员的质量报告。

## 何时使用

- 需要把一份或一批行程附件变成结构化线路内容或详情页。
- 需要核对某份附件整理结果的质量：哪些字段有依据、哪些原文没有被整理进去。

整理结果是**待审核的候选内容**，不是已发布内容。技能不写入任何业务系统，也不发布。

## 运行

依赖：Python 3.11+、`pydantic`、`anthropic`，以及 Poppler（`pdftotext`、`pdfinfo`、`pdfimages`、`pdftoppm`）。转写 DOCX 图片、生成封面图还需要 `Pillow`。

```bash
python scripts/run.py --file /private/route.docx --out /private/out --env /private/model.env
python scripts/run.py --corpus /private/corpus --out /private/out --env /private/model.env
python scripts/run.py --corpus /private/corpus --out /private/out --env /private/model.env --vision
python scripts/run.py --corpus /private/corpus --out /private/out --render-only
```

- `model.env` 提供 `ANTHROPIC_API_KEY`、可选的 `ANTHROPIC_BASE_URL`，以及 `ROUTE_KIT_MODEL`（或 `TOUR_MODEL`）。env 文件里的值优先于进程环境。不要把密钥写进命令、脚本或输出。
- 批量模式读取目录下的 `manifest.json`：`[{"code","name","days","file"}]`，其中 `days` 是业务系统登记的天数，用来比对；没有 `file` 的条目会生成"缺少附件"页。
- `--vision` 转写图片里的文字（见下文"图片转写"），需要支持图片输入的模型。
- `--only CODE ...` 只处理指定线路，索引页保留其他线路的上次结果。
- 输出：`routes/<code>.json`、`routes/<code>.html`、`routes/<code>.cover.jpg`（有封面图时）、`index.html`、`summary.json`。模型结果缓存在 `out/.cache`，重跑只为变化的部分付费。
- 附件和输出都是供应商资料，只放在私有目录，不提交到代码仓库，不上传到公开地址。

## 处理流程

1. **读取**（`reader.py`）：DOCX 按正文顺序读段落和表格行，表格保留列位置（空格子也占位）；PDF 用 `pdftotext` 读文字层并记录页码，识别"有图片但几乎没有文字"的页，以及文字层乱码的页（字体映射错误时，文字看上去是中文，但大多落在罕用字上：一页里不属于最常用 3755 个汉字的字超过 4% 就判为乱码）。去掉多页重复的页眉页脚（含餐、住、费用字样的行不删）和页首页尾的页码；表格被按单元格顺序读乱的页（同一页上的天标签不是递增的）改用版式读取重读，只有重读后标签顺序恢复才采用；仍然错乱而且能读图片时，这一页改用图片转写。删掉的每一行记在 `quality.removed`，审核视图可查。
1b. **图片转写**（`vision.py`，`--vision` 时）：PDF 里有图片但几乎没有文字的页、文字层乱码的页（丢弃这页的文字层，整页转写）、没有文字层的扫描 PDF、DOCX 正文里的图片（去掉小图标和重复图片），逐张交给模型照抄文字，并判断是封面、行程、表格、照片还是装饰。转写的文字放回图片原来的位置，成为带 `origin: "image"` 的证据单元，和正文一样被引用、被校验；照片和装饰图不产生文字。第一张封面图缩小后作为详情页封面。
2. **切分**（`segment.py`）：长行按句子切成证据单元，每个单元有编号，之后所有字段都引用这些编号。按"第 X 天 / DAY-X / Dx / 第 X–Y 天 / 第 X 天至第 Y 天"找出天数；同时存在概览表和详细行程时，文字多的一组作为逐日行程，另一组作为每天的补充依据。最后一天在条款标题或另一组天数标题处截断。只有一天的行程识别不出天数（`NO_DAY_HEADERS`），页面只显示原文。
3. **边界复核**（`extract.py`）：规则找不到任何天数标签时，先由模型判断这份文件是不是线路（商品介绍、合同这类不是线路的文件在这里停下，报 `NOT_ITINERARY`，不生成详情页）；是线路的（标签是图形、竖排，或只有日期行，或是一日游），由模型按内容给出每一天的起点；结果必须是完整的 1..N 递增序列，且与登记天数一致，否则不采用。规则已经找到天数的附件不受影响。PDF 的天数标签可能不在当天开头，由模型根据内容确定每天的起点，代码检查结果递增且不偏离标签太远，否则沿用规则。每份附件都由模型确定最后一天在哪里结束：接待标准、服务标准、费用栏目紧跟在最后一天后面时，标题写法各不相同，这些属于条款，不属于当天行程。
4. **提炼**：一次调用整理封面和条款（含封面卖点 `selling_points`），每天一次调用整理逐日节点、三餐、住宿。提示词见 `prompts.py`。
5. **校验**：由代码决定哪些结果能保留（`extract.py`）。
   - 有名称的节点，名称必须出现在所引用的原文里；
   - "无购物"由模型判断，说法不限；代码只检查它逐字引用的那句话在引用的原文里，并且带有"没有"的字眼；
   - 照抄类字段（条款、提示、当天备注、"含…"标签、酒店名、替代安排）大部分文字要在所引用的原文里；线路级条目必须有引用，没有引用的删除；
   - 页面显示的数字（时长、价格、航班时间、晚数、起订人数等）必须在原文里作为完整数字出现（"1" 不算出现在 "10" 里）；
   - "入内""外观""含门票""免费参观""赠送""推荐""特别安排"等属性，以及"自费""购物"节点类型，要在节点名称附近找到对应词语；"不含门票""不入内"这类否定说法不算依据；
   - 模型概括的字段（当天标题和概括、节点描述、交通节点名称）只检查数字，审核视图标注"模型概括"；
   - 不合格的删除、清空或改回"未说明"，并记为问题项；
   - 一天里被删除的内容较多时，带着问题清单重试一次，保留两次中问题较少的结果。
   - 当天的"行：""住宿：""餐："行和"独家安排""自费推荐行程"这类标题不作为提示或节点；封面卖点只保留 3–12 字的短标签；封面图和正文重复的同一条只保留一次。
6. **组装与渲染**：生成 `RouteContent`（`models.py`），渲染详情页（`src/route_kit/templates/route.html`）和索引页。涉及费用、购物、条件的原文没有被任何字段引用时，原样挂到当天备注或温馨提示，标记 `auto`，审核视图显示"原样挂入，待审"。覆盖分三类统计：直接引用、推断归入（续句、短标签）、原样挂入。

## 口径

- **自费项目**：客人要另外付费才能参加的项目：写明"自费""另付""自愿参加/选择/乘坐/消费"的项目，以及需付费的升级。免费升级、赠送、已含门票不算；"自愿放弃""自愿取消"这类与具体项目无关的说法不算。
- **含餐的表达**：数据里只有四种状态，页面统一显示为"含""自理""不适用""未说明"，原文写的是空、"/"、"×"、"不含""敬请自理"还是别的，都归入这四种；原文里有具体说明（团餐、特色餐、酒店早餐）时接在后面。表格里的 √ 表示含，× 表示不含。
- **餐数**：逐日行程显示原文明确写出的用餐，不用全程总数去推断没写的那几餐。费用包含写明的全程餐数单独显示，两者不一致时审核视图提示。

## 修改原则

改一处问题前，先判断该由哪种机制解决，不要直接加正则：

- **语义判断交给模型**：某条内容属于哪一类、一段文字从哪里开始或结束、标签被版面拆开后怎么理解。这类写法随供应商变化，靠提示词说明规则，代码只检查结果。
- **有依据的统计信号交给代码**：例如乱码判断用"罕用字占比"，不逐个列举乱码字。
- **代码只做校验，不重新判断语义**：校验的目的是拦住凭空捏造的引用、数字和属性；引用里出现的词只需能支撑结论，不要为每种写法各加一条规则。
- **加规则前先找根因**：先看内容在流程的哪一步丢了或放错了位置（这次是接待标准被当成最后一天，模型在条款调用里根本看不到），再决定改哪一步。同一个现象需要第二条正则时，说明机制选错了。

## 页面

页面显示时整理供应商的标点：`<某餐>` 显示为「某餐」，标签后的 `---` 显示为冒号，数字之间的 `--` 显示为"–"（13:30–15:50），地名之间的 `——` 显示为"—"，并去掉句尾分号。JSON 保留原文写法。

同一份数据，电脑宽度下是三栏（目录 / 逐日行程 / 侧栏），手机宽度下是单栏（天数标签 + 一天一屏）。三种视图：

- **客户看**：对客内容，另有"费用与安排提示"汇总自费、购物、可能调整的安排和需另付的费用。
- **审核看**：显示"原文未说明"标记、"模型概括""图片转写""原样挂入，待审"标记、每天的自动校验问题、未被整理的高风险原文、读取时删除的行。
- **原文对照**：显示当天原文；点击节点，对应原文加深高亮。

详情页是内部审核页：全部原文、问题项和删除记录都嵌在页面数据里，只是客户视图不显示。对客发布时用 JSON 里的字段重新渲染，不要直接把这个页面发给客户。

设计依据见 `reference/`。

## 审核要点

交付或审核时说明以下内容：

- 附件天数与登记天数是否一致；
- 整理成功的天数、直接引用比例；
- "原样挂入，待审"的原文逐条处理：改写进对应字段，或确认保留原样；
- 高风险未归入原文逐条处理：涉及费用、购物、条件、取消的原文必须有去处；
- 读取时删除的页眉页脚是否误删了内容；
- 标着"图片转写"的内容逐条对照封面图核对：模型照抄图片可能看错字；
- 属性被改回"未说明"的节点，由人工对照原文补上，或保持未说明。

审核时注意：
- "外观"不等于不含门票，"推荐"不等于包含，"特别安排"不等于赠送；
- 附件里的价格信息不是实时报价，另付费用和单房差不能与团费相加当作总价；
- 购物点只写名称、类型和停留时间，不写产品功效。

机器校验只证明"结果有原文依据"，不证明供应商写的内容本身正确。
