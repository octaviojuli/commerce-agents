# Jev 在云仓顾问端的适用性与实测报告

2026-09-28。代码参照 Claude 分支 `advisor-v3-p0`，提交 `489816e5bb7b8db3f8ba9ad167e6a9610d53e6a6`。本轮只新增评测与报告，没有修改业务代码、切换在线模型或部署 ECS。

**结论：值得试接，优先做会话动作判断；事实核验可作为辅助检查。现阶段保留现有模型负责需求完整抽取和回复生成，所有交易权限与计算继续由程序负责。**

## 能力与可借鉴实现

Jev 接收上下文和一组问题，返回选择、评分或真假概率；它不生成自由文本。这与现有 `extract → decide → draft` 中的部分 `decide` 职责相近，不等同于完整的 `Extraction` 或 `ReplyDraft`。[官方介绍](https://docs.typesafe.ai/introduction)

| 能力 | 在本项目中的落点 | 适用边界 |
| --- | --- | --- |
| Choice：从给定选项中选择 | 在程序允许的动作中选下一步；判断客人是否明确选择线路 | 不能新增动作、授权执行或代替人确认 |
| Choice：选择已有候选值 | 判断人数类别、每个儿童的占床、预算金额候选、必去与举例目的地 | 候选先由程序或现有模型提供；不能直接替代完整需求抽取 |
| Choice：核验语义 | 判断回复是否改变原文费用、否定词、年龄条件、登记要求 | 必须传完整相关原文；低置信度交复核 |
| Noul / Score：判断、评分 | 对已通过权限与硬条件筛选的线路评估亲子、节奏、购物适配 | 不计算价格，不证明库存，不放宽必去国家 |

官方已提供 [Python SDK](https://github.com/typesafe-ai/typesafe-sdk-python)、[引用核验](https://docs.typesafe.ai/cookbooks/citation_check)、[候选值抽取](https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook) 和 [检索片段筛选](https://docs.typesafe.ai/cookbooks/classifying_rag_passages) 示例，可以复用设计。本轮按官方 HTTP 协议写了独立评测客户端，未安装新的运行时依赖。

官方明确列出了数值计算、日期比较、多层推理、长而无关的上下文及对抗性内容的局限。销售价减结算价、日期窗口、报价版本和儿童逐人计价应继续留在程序中。[模型局限](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

## 实际调用与方法

- 已成功使用提供的密钥调用官方 `https://api.typesafe.ai/v1/systemone`，固定模型 `jev-1.13.0`；另验证模型列表接口返回 200。
- 81 次 Jev 判断调用，包含 60 个不同业务案例、4 次连通性试跑、12 次重复测试、4 次英文问题表述探测，以及1次上游原文丢失边界测试。共 121 个问题，全部 HTTP 200，返回字段与本轮问题类型校验通过。
- 首批 48 例及预期答案在调用前写入；后续 12 个业务难例是探索性补测。预期答案未发送给 API，未为了结果修改原题与答案。
- 18 个动作案例中包含两条各5轮的人工构造会话状态序列；这是冻结状态回放，不是运行商户服务、持久化会话和浏览器页面的完整验收。
- 全部输入均为虚构旅游案例，没有发送真实客户、证件、供应商附件或生产数据库内容。密钥经隐藏输入进入进程内存，未写入评测文件；调用进程已退出。
- 耗时为本机到 API 的完整请求时间，包含网络和服务处理，使用连接复用、最多2个并发；不代表 ECS 链路和用户完整对话耗时。

## 结果

| 不同业务场景 | 符合预期 | 实际覆盖 |
| --- | ---: | --- |
| 会话动作与明确选线判断 | 18/18 | 重新找线、点名查线、比较、犹豫、询价、报价分享、行前待办 |
| 有限候选需求判断 | 8/8 | 总人数不等于成人数、逐儿童占床、德法意瑞、举例目的地、出发窗口、预算变更 |
| 线路适配判断 | 6/6 | 亲子慢游、购物冲突、购物未知、雪山偏好、老人徒步冲突、缺少必去国家 |
| 事实及条件核验 | 26/28 | 费用反转、年龄限制、餐食、酒店保证、登记提前量、来源未知 |
| **合计** | **58/60** | 94 个预期检查项中 92 个符合预期 |

首批48例中位耗时 **281 ms**，P95 **486 ms**；全部81次中位耗时 **281 ms**，P95 **815 ms**，最慢 **1465 ms**。小样本且多为短文本，不能据此估算生产吞吐。

Jev 共计 51,215 输入 token、4,811 输出 token。按官方当前输入价每百万 token **0.042 美元**、输出免费估算，本轮 Jev 费用约 **0.00215 美元**。这是公开单价估算，未读取账户账单，也不含现有模型对比费用。[官方模型与价格](https://docs.typesafe.ai/models)

## 错例和置信度

| 案例 | 原文 → 对客说法 | Jev 判断 | 置信度 |
| --- | --- | --- | ---: |
| H03 | “全程无购物，不含自费景点门票” → “全程无购物无自费” | 错误允许 | 0.07 |
| H12 | “儿童餐需要提前两天登记” → “儿童餐要预先登记” | 错误允许，遗漏提前两天 | 0.17 |
| F07 重复测试 | “儿童餐需要提前两天登记” → “儿童餐需要提前登记” | 首次及两次复测拦截，第三次复测错误允许 | 错判时 0.04 |

12 次重复调用中11次符合预期；不能认为同样输入必然得到同样选项。将题目表述改成英文的4次探测均判断正确，但部分仍然低置信度，不能据此认为中文问题已解决。

以 **0.8** 为观察阈值，18个动作案例有14个达到阈值，另4个未达到；28个事实案例有22个达到阈值，另6个未达到。这批高置信度结果未见错误，但不能据此直接启用执行，也不足以证明生产可靠性。

事实核验的接法应为：达到该类检查阈值的 `safe` 才有资格继续通过其他校验；确定的 `unsafe` 拦截或要求改写；判断不确定、超时和服务错误交现有模型/人工复核。0.8仅用于本次分析，尚未完成生产阈值校准；普通偏好排序不需要套用同一门槛。官方的 `confidence` 是概率分布的统计量，不能简单理解为“这句话有80%概率正确”，Noul也没有同一种置信度字段。[置信度说明](https://docs.typesafe.ai/confidence)

## 与现有代码的对照

现有配置模型为 `deepseek-flash`。调用当前 `TypedModel.call("decide", ...)` 回放相同18个动作场景：

| 对照项 | Jev 原型 | 当前模型与提示 |
| --- | ---: | ---: |
| 与预设动作标签完全一致 | 18/18 | 15/18 |
| 中位调用耗时 | 284 ms | 911 ms |
| 有效结构结果 | 18/18 | 17/18 |

这个对比只支持“窄动作判断值得试接”：当前模型还输出意图、目标列表、天数定位、线路名等完整 `Decision`，Jev 原型只输出动作和是否明确选中单条线路，输出任务量不同。不能把耗时差当作完整顾问对话提速比例。

当前模型两个标签差异（D14、D15）在代码中进入同一个事实读取分支，不应算成两个确定的业务失败。D12点名查线未得到有效返回；单独复查时，两次内部尝试仍报告 `invalid_output`。本次未进一步修改该问题。

纯文本 `copilot_reply.supported()` 对同一组28个事实案例符合15个，出现9次错误允许和4次错误拒绝；Jev为26/28。这只是该函数的直接对照，不是整个线上回复链路的通过率。

最重要的接入限制是 **原始证据不能提前丢失**：当前 `copilot_plans.clip()` 把“仅限6岁以下儿童。早餐免费。其他年龄按成人标准收费”截成“早餐免费”。若只把这个截断版本送给 Jev，边界测试 B01 得到 `safe`。只有连同完整相关原文送入，模型才有机会发现适用条件丢失。

另外几个已有缺陷仍需程序修复：

- “可以按原需求重新找线吗？”即使模型选对 `search_routes`，当前后续问句分支仍可能覆盖动作；不能只换模型。
- 旧报价的版本、人数和需求依赖必须先校验，不能要求 Jev 从一个金额判断是否过期或串用了旧需求。
- 单个儿童已知占床不能推广到全部儿童。Jev这次正确保留5岁儿童为未知，但后续 `Rooms` 与计价逻辑仍需保留这个未知状态。

## 推荐接法与下一步验收

一期先增加可切换的 `DecisionBackend`，让 Jev 接收最小必要的脱敏状态和程序计算的允许动作。先记录其判断与当前模型的差异，不改变业务执行；积累验证后再让高置信度的窄动作判断生效。完整目标列表、意图、线路名和天数定位仍需完成适配，当前评测原型不是可直接替换的完整接口。

事实核验作为第二个试点：传入“完整相关原文＋草稿中的主张”，按问题批量检查，保留证据定位。不能用它自动发布供应商行程、自动批准报价或取代人工采纳商户回复。

现有模型继续负责需求完整抽取、顾问解释、对客草稿与复杂多轮理解。硬筛选、价格与利润计算、数据权限、版本校验、确认和一期禁用的占位/下单继续由程序管理。

真正上线前还需要：更大且独立留出的中文评测集；完整 `Decision` 契约测试；真实商户连接下的多轮会话、失败回退与回放；ECS到官方接口的耗时与可用性验证。本轮API能力测试不替代这些验收。

官方称请求/响应不用于模型训练，但普通账户不能据此认定为零留存；企业 ZDR 需单独开通。后续仍应沿用项目的姓名、证件和内部价格保护，仅发送必要脱敏上下文。[官方数据说明](https://docs.typesafe.ai/models)、[数据条款入口](https://docs.typesafe.ai/legal)

## 官方 Skill 对照补充

用户随后提供了 [Typesafe 官方 Skill](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md)。已完整阅读并核对相关官方示例；以下是方法补充，没有新增 API 调用，原始结果保持不变。

Skill 支持此前“程序掌握流程和权限，Jev提供语义判断”的方向。它也提示：低置信度可能来自多个同样合理的选择；业务后果、输入证据、候选完整性和程序如何组合结果，都必须纳入验收。因此，当前错例只能证明这套提问与组合方式存在问题，不能直接定义模型永久能力上限。

需要补强的设计如下：

| 改进 | 本项目中的具体做法 | 验收重点 |
| --- | --- | --- |
| 动作与参数一起判断 | 同次请求判断动作，并分别判断哪些可见线路参与比较、是否明确选线、指向哪一天；只使用当前分支需要的答案 | 不把“比较第一、第二条”简化成只选一条；无关参数的不确定性不阻塞回答 |
| 事实检查按条件拆分 | 对完整相关原文分别检查费用与否定、人群范围、提前登记要求；可确定的数值和日期一致性由程序核对 | 任一相关必要条件丢失就不能放行，不能用其他维度高分抵消 |
| 候选缺失有明确出口 | 候选值加入“未提及/不在候选中”，记录原文位置；独立检查用户是否真的提供了该字段 | 未提年龄、未提供房型、线路名未进入候选时不强行选值 |
| 阈值按后果区分 | 方向排序允许多个合理答案；选线确认、价格及条款事实使用分别验证过的门槛 | 报告覆盖率、错误放行率、误拒率和回退率，而不只报告标签命中率 |
| 只复用仍有效的判断 | 保存证据与需求版本；权重调整可以复用原评分，事实或问题含义变化需重新判断 | 异步结果返回时重新校验版本，防止旧需求的结果覆盖新需求 |

动作和已有候选参数的组合可参考 [函数调用示例](https://docs.typesafe.ai/cookbooks/function_calling)；独立问题可批量提交，但同次请求里的问题不能读取彼此的答案，需要新证据才能回答的问题仍应分下一次请求。[并行问题模式](https://docs.typesafe.ai/patterns/fan-out)

线路排序可以分别保留亲子、节奏、住宿等评分，随后按需求调权；必去国家、购物禁忌、权限和可售条件仍是独立约束，不能被加权总分抵消。[组合评分模式](https://docs.typesafe.ai/patterns/composite-scoring)

后续针对本轮 H03、H12、F07 错例，应保留原问法作对照，测试拆分条件后的问法；再用未参与改题的同类新案例验证。补上候选遗漏、多条线路指代、证据不足、服务失败及会话状态变化测试，最后观察实际页面行为。上述改法尚未实测，不能据此上调58/60结果。
