# 逐日行程的统一内容层

PDF/DOCX 是事实来源。解析器负责读取文件，云仓负责统一内容结构，模型负责在原事实与限制内改写表达。页面读取持久候选或人工发布版本，不在打开页面时调用模型。

## 字段与展示

| 字段 | 用途 |
|---|---|
| `day.title` | 当天地点顺序或主题，不含公里数和车程 |
| `day.travel_reference` | 原文包含里程、时长的完整路线，避免把数字错配到路段 |
| `day.summary` | 当天简述，概要与详情共用 |
| `day.blocks` | 有顺序的交通、游览、自由活动、自费、购物、提醒段落 |
| `day.meals/hotel/flights` | 原有餐食、住宿、参考航班的独立字段 |
| `day.text` | 原始逐日文字；原附件与原解析继续单独保留 |

标题和参考交通分栏；正文用小标题及自然段，三餐与住宿独立显示。原附件补充栏目默认收起。客户投影只含展示字段，排除原文定位、模型报告、审核信息和内部业务数据。

## 处理及审核

1. 只为当前在架线路、最新附件解析创建候选；完整连续天号是模型处理前提。
2. 统一标题，将带里程的旧标题保存到 `travel_reference`，不猜测缺失的交通方式与时长。
3. 模型读取单日文字，返回明确引用来源段落的简述及正文。不能执行资料里的指令。
4. 校验来源覆盖与顺序、数字、限制关键词和文本上限，再独立调用模型核对新增、遗漏及含义变化。
5. 自动核对失败保留原文及原因。通过后的内容仅写入云仓私有候选，不能自动发布。
6. 人工对照原文，保存修订，再完成既有审批。人工稿、旧发布版本和历史附件均保留。

机器核对不是准确率保证。原文自身可能错误或矛盾，模型不能用常识改写事实。缺少天号或不同资料冲突，需要业务人员核实。模型失败不应显示为“已核验事实”。

## 运行与可追溯性

`daily-editor-2` 增加 `route_facts.py`。只依据原文和已有景点／地点字段识别对象，核对数值与上下限、游览方式、明确费用项目、航班标识及限制条件的对应关系。有限同义词先规范化；同一对象的重复声明和顺序保留。重新断句与对象名中的空格不应导致误判。规则有输入与声明数量上限，无法安全处理时保留原稿。

`fact_checks` 随私有候选报告保存原段编号、对象、原声明及未采用改写差异，商户可按异常筛选并定位原稿日期。规则识别范围有限，代词、复杂条件作用域和未识别实体仍需语义核对与人工审核。此处的“声明”表示供应商写过，不表示现实事实已被外部核实。新策略生成独立候选，旧候选与人工稿继续保留；未发布稿不进入顾问或客户页面。

`route_content_candidate` 保存解析 ID、原资料摘要、策略版本、模型标识、逐日进度和核对报告。每次处理一天，三分钟租约，完成时复查来源、连接和展示状态；租约失效不能写入，来源已变化的结果作废。已完成记录不可覆盖。每个模型调用设置超时且不自动重试；后台进程故障可续接，反复故障的日期保留原文待人工处理。模型接口仅配置在独立内容任务中。

Skill 的 `--edit --model-config /private/model.env` 使用同一套能力。每次调用处理一天，写 `edited-candidate.json` 与私有核对报告；原始 `candidate.json` 不变。重复调用继续进度，不自动写云仓、不自动发布。

结构化输出采用当前 Anthropic 兼容客户端与 Pydantic 校验，沿用[类型化输出与验证](https://pydantic.dev/docs/ai/core-concepts/output/)的做法，不引入另一套代理框架。
