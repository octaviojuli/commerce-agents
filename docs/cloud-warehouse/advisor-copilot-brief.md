# Brief：顾问搭档（顾问端智能体与交互）重构

## 0. 结论先行

- **产品形态**：以手机原型 [`advisor-mobile-prototype-v4.html`](advisor-mobile-prototype-v4.html) 为准，共 19 屏、6 章。顾问端定位为顾问的幕后搭档：客人的话粘贴进来，搭档负责理解、记住、查清、比较、核对、起草，再把可以直接发回微信的内容交还给顾问。
- **核心数据**：每一单只有一份**有版本的需求状态**（`DealState`）。客人每改一次主意，就产生一个新版本；对话中的其他一切（比较、推荐、报价、确认）都基于某个版本。
- **分工**：
  - **模型负责理解和回填**：意图、变更单、需求清晰度、顾虑、推荐理由、回复草稿，全部是类型化的结构化输出。
  - **程序控制流程**：版本、连锁影响、阶段关口、允许的动作、检索、核价、校验，全部由确定性代码完成。
  - **顾问做决定**：模型提出的变更必须经顾问采纳才生效；发给客人的内容由顾问确认后发出。
- **架构**：**一个智能体 + 一组类型化模型函数 + 若干工具 + 按阶段加载的技能 + 程序控制的回合管线**。每一回合都走固定的管线；智能体只能在程序给出的工具和动作范围内行动。
- **下一步动作**：用类型安全的结构化输出评估需求，但**不让模型自由选择下一步**。程序先算出“当前允许的动作”（枚举），模型只在这个集合内选择。
- **判断类问题交给可替换的“决策后端”**：意图、顾虑、下一步动作、确认覆盖哪些项等，都是在已知选项里做判断，可以由 TypeSafe 的决策模型 Jev 回答，也可以由现有大模型回答。先在评测集上比较，再决定用哪个（6.1 节）。
- **与现有实现的关系**：保留 Codex 已实现的数据层、租约、报价、分享和客户投影；替换目前“一个 ShoppingAgent 靠 8 条提示词规则自己决定流程”的做法。第 14 节有逐个模块的对照表。

本 Brief 替代 `advisor-workbench-brief.md` 中的智能体和交互部分。业务和模型缺陷的修复见 [`advisor-workbench-fixes-v2.md`](advisor-workbench-fixes-v2.md)；其中 N1、N3、N4、N5、N8 的根本解决方案在本 Brief 里。

## 1. 为什么要重构

用真实模型和本地目录副本（289 条线路）跑了 15 组模拟需求、36 轮对话，结论是：检索和团期数据全部准确，没有编造。但有三类问题出在架构上，改提示词解决不了：

| 问题 | 现象 | 根因 |
|---|---|---|
| 流程靠模型自觉 | 顾问说“要 2 间房，帮我询价”，模型又去检索线路、退回选线；空回复出现 5 次 | 流程规则写在提示词第 3–5 条，模型可以不遵守；`close_on_presentation` 在模型还没写回答时就结束了本轮 |
| 理解的结果被程序覆盖或截断 | “土耳其和希腊”只剩希腊；“去过法国”被记成要去；贴长消息后上下文被截到 6000 字 | 正则规范化覆盖模型结果；证据字段保存整条原话，状态快照超长 |
| 状态只有“当前值”，没有变化 | 客人改需求后，旧候选、旧报价、旧备注的处理散落在多处代码中，部分被静默清空 | `TripBrief` 是单一可变对象，没有版本，也没有“变更 → 影响”的规则表 |

## 2. 目标与非目标

**目标**
1. 覆盖原型 v4 的全部流程：模糊需求、需求对接、需求变化、客人记忆、线路查询、比较与优缺点、推荐理由与方案、回答追问、问答簿、行程备注、团期选择、确认单、正式报价、证件识别、出发前清单。
2. 每一回合都有文字回答，并附可以直接发给客人的草稿。
3. 客人说过的、推断的、顾问改过的内容分开记录，全程可以追溯到原话。
4. 模型说出的每一条事实，都能对应到程序查到的数据；没有依据的，一律标“待核实”。

**非目标（本期不做）**
- 占位、下单、支付：原型里标“二期”的部分。本期界面预留位置，但不接供应商接口。
- 客人直接与智能体对话：客人只看顾问发出的方案页。
- 多个智能体协作。

## 3. 设计原则

1. **状态是唯一依据**：智能体的每次输出都基于某个 `DealState` 版本号；版本变了，旧输出自动标为过期。
2. **理解和执行分开**：模型函数只返回数据，不产生副作用；副作用只发生在程序代码里。
3. **类型即边界**：模型的所有输出都是 Pydantic 模型，通过强制工具调用返回；校验不通过就重试一次，再失败则降级，并在页面上说明，不静默忽略。
4. **事实必须有来源**：回复里的价格、团期、余位、行程内容，都必须引用工具结果的 `fact_id`；回复校验器负责检查。
5. **一轮只问一件事**：追问由程序根据缺失项的优先级选出，模型只负责措辞。
6. **推断不当事实**：推断的字段只影响排序和提示，不作硬条件，也不能写成“客人说过”。

## 4. 总体架构

```
 顾问 H5 ──HTTP/SSE──▶ Advisor API (FastAPI)
                          │
                 ┌────────▼─────────┐
                 │  Turn Orchestrator │  程序：一回合的固定管线（第 5 节）
                 └───┬─────┬──────┬──┘
         类型化函数   │     │      │ 受约束的智能体
   ┌─────────────────▼┐ ┌──▼────────▼───────────┐
   │ extract()   大模型 │ │ Copilot Agent           │  一个智能体
   │ decide()  决策后端 │ │  · 按阶段加载的技能      │
   │ backfill_memory() │ │  · 程序给出的工具子集    │
   │ draft_reply()     │ │  · 只读状态快照          │
   └─────────┬────────┘ └──────────┬─────────────┘
             │ ChangeSet / Memory      │ 工具调用
   ┌─────────▼────────────────────────▼─────────────┐
   │ Deal Engine（纯 Python，确定性）                   │
   │  版本账本 · 影响规则 · 阶段关口 · 允许动作 · 清晰度   │
   └─────────┬───────────────────────────────────────┘
             │
   ┌─────────▼────────────────────────────────────────┐
   │ Domain Services（现有云仓）                          │
   │  目录检索 · 线路内容(route-kit) · 团期 · 报价 · 分享 ·  │
   │  客户投影 · 证件 OCR · 会话租约                       │
   └──────────────────────────────────────────────────┘
```

对第 4 个问题的回答：**是“一个智能体 + 工具 + 技能 + 程序控制”，但智能体不控制流程**。具体分成四类构件：

| 构件 | 是什么 | 谁决定何时运行 | 有无副作用 |
|---|---|---|---|
| 抽取与起草函数 | 一次大模型调用，输出 Pydantic 模型：`extract()` 抽取字段值，`draft_reply()` 起草回复 | 回合管线（程序） | 无 |
| 决策函数 | 对状态回答类型化的判断题：单选、是非、打分。由决策后端执行（Jev 或大模型），返回答案和置信度 | 回合管线（程序） | 无 |
| 智能体 | 一个带工具的多步模型循环，负责组织本轮要给顾问看的卡片和回答 | 回合管线；每回合最多运行一次 | 只通过工具产生，工具受程序限制 |
| 工具 | 领域服务的类型化入口，例如检索、团期、报价 | 智能体调用；只能调用程序本轮开放的那些 | 只读，或经程序校验后写入 |
| 技能 | 按阶段加载的指令包：说明、输出模板、少量示例 | 程序按阶段选择，模型不能自选 | 无 |

**为什么不用多智能体**：一单就是一个上下文，拆成多个智能体会产生状态同步和前后说法不一致的问题，延迟和成本也会翻倍。需要专门能力的地方用类型化模型函数，它们无状态，也更容易测试。

## 5. 一回合的管线

每条顾问输入（粘贴的客人消息、顾问自己的话、按钮）都走同一条管线，由 `TurnOrchestrator` 执行，并持有现有的会话租约（`conversations.begin/finish/interrupt`）。

| 步骤 | 执行者 | 输入 | 输出 | 超时 | 失败时 |
|---|---|---|---|---|---|
| 1 读状态 | 程序 | 会话 ID | `DealState@vN`、客人记忆、最近 6 轮摘要 | — | 报错并释放租约 |
| 2a 抽取 | 大模型 `extract()` | 本轮原文 + 状态快照 | 字段变更（值、原话证据）、问题原文 | 8s | 重试一次；仍失败则跳到第 6 步，只起草澄清 |
| 2b 判断 | 决策后端 `decide()`，与 2a 并行 | 本轮原文 + 状态快照 + 候选选项 | 意图、顾虑、选定的线路或日期、问题主题，各带置信度 | 1s（Jev）/ 5s（大模型） | 置信度低于阈值时交给顾问确认，或转大模型复核 |
| 3 合并 | 程序 Deal Engine | 变更单 | 待采纳的 `ChangeSet`，或自动采纳后的 `DealState@vN+1`（规则见 7.3），以及影响清单 | — | — |
| 4 评估 | 程序（+ 模型函数） | 新状态 | 清晰度、关口、允许动作、追问候选 | 5s | 清晰度模型失败时只用程序打分 |
| 5 行动 | 智能体 | 允许动作、阶段技能、状态快照 | 工具调用产生的卡片、事实 `fact_id` 列表 | 25s | 保留已产出的卡片，第 6 步照常执行 |
| 6 起草 | 模型函数 `draft_reply()` | 状态、本轮卡片的事实、问答簿 | `ReplyDraft`：给顾问的一句结论 + 给客人的草稿 + 快捷回复 | 8s | 用模板生成最小回复，一定有文字 |
| 7 校验 | 程序 | `ReplyDraft` | 事实引用、承诺词、编号可见性、阶段合法性 | — | 删除不合格的句子或按钮，记日志 |
| 8 保存 | 程序 | 全部结果 | 事件、状态版本、问答簿、记忆 | — | 事务回滚，本轮标为中断 |

要点：
- 第 5 步的智能体可以不调用任何工具。只问问题的回合就是这样，**文字回答永远由第 6 步产生**，从结构上消除空回复（修复清单 N1）。
- 按钮操作（看团期、询价）跳过第 2 步和第 5 步，直接执行对应工具，再进入第 6 步。
- 整条管线把事件以 SSE 流式推给前端：理解结果、卡片、草稿依次出现。

## 6. 类型化契约

所有模型函数都用“强制工具调用 + Pydantic 校验”。模型只看得到 JSON Schema，看不到程序内部状态。示意如下：

```python
class Intent(StrEnum):
    NEW_NEED = "new_need"        # 新需求
    CHANGE = "change"            # 改需求
    ASK = "ask"                  # 问线路、问政策
    CONCERN = "concern"          # 表达顾虑
    DECIDE = "decide"            # 做决定：选线、选日期、确认
    CHITCHAT = "chitchat"        # 寒暄
    UNKNOWN = "unknown"

class Evidence(BaseModel):
    quote: str = Field(max_length=120)   # 原话片段，程序校验必须是本轮或最近 5 轮原文的子串
    turn: int                             # 来自哪一轮

class FieldChange(BaseModel):
    field: DealField                      # 枚举：destinations / window / days / party / rooms / budget / ...
    op: Literal["set", "add", "remove", "clear"]
    value: Json                           # 按 field 的类型二次校验
    source: Literal["said", "inferred"]   # 模型不能写 advisor 或 explore
    evidence: Evidence | None             # said 必填
    reason: str = ""                      # inferred 必填：为什么这样推断

class Question(BaseModel):
    text: str
    topic: QaTopic                        # 住宿 / 购物 / 儿童 / 老人 / 签证 / 退改 / 景点 / 费用 / 航班 / 其他
    route_ref: str | None                 # 问的是哪条线路（已展示过的编号）

class Understanding(BaseModel):          # 由 extract()（大模型）和 decide()（决策后端）的结果合并而成
    intents: list[Intent]                 # decide：一句话可以有多个意图
    changes: list[FieldChange]            # extract
    questions: list[Question]             # extract 抽出原文，decide 判断主题
    concerns: list[Concern]               # decide 判断已知顾虑，extract 补充新顾虑
    decision: Decision | None             # decide：{kind: pick_route | pick_date | confirm | reject, target}
    confidence: dict[str, float]          # decide 给出的各题置信度

class NextActionPick(BaseModel):
    action: AllowedAction                 # 只能是程序本轮给出的枚举值之一
    reason: str
    ask: ClarifyQuestion | None           # 需要追问时，只问 1 个，字段来自程序给出的缺失项

class ReplyDraft(BaseModel):
    to_advisor: str = Field(max_length=80)          # 一句结论
    to_customer: str = Field(max_length=400)        # 微信草稿
    claims: list[Claim]                             # {text, fact_id}：草稿里每条事实对应的工具结果
    chips: list[Chip]                               # {label, action: AllowedAction | "ask:<题目>"}
    customer_may_ask: list[str] = Field(max_length=3)
```

**Pydantic 与 Jev 的关系**：Pydantic 是类型定义和校验库，负责规定“答案长什么样”；Jev 是回答这些类型化问题的模型。二者配合使用：Pydantic AI 通过 `TypeSafeModel` 直接调用 Jev，用 Pydantic 类型定义题目。上面的契约里，`Intent`、`Concern` 的标签、`Decision` 的目标、`NextActionPick.action`、问题主题都是判断类字段，可以由 Jev 回答；`FieldChange.value`、`ReplyDraft` 的文字需要自由输出，只能由大模型生成。

**对第 3 个问题的回答**：类型安全的结构化输出**用在“评估”上，不用在“决定”上**。

- **评估**：意图、变更、清晰度、顾虑、推荐理由都用强类型输出。好处是可以测试、可以回放，程序能逐字段校验，失败也能降级。
- **决定**：下一步动作的可选集合由程序算出；模型输出的 `NextActionPick.action` 类型本身就是这个集合的枚举，Schema 在每一回合动态生成。模型选不到集合外的动作；即使选了，程序也会拒绝。

### 6.1 决策后端与 Jev

**接口**：定义 `DecisionBackend` 协议，输入是状态快照和一组类型化判断题，输出是每题的答案、概率分布和置信度。先提供两种实现：
- `LLMDecisionBackend`：现有大模型，强制工具调用，置信度由模型自报，只作参考；
- `JevDecisionBackend`：通过 Pydantic AI 的 `TypeSafeModel('jev-latest')` 调用。

**判断题清单**（全部是枚举、是非或打分，没有自由文本）：

| 题目 | 类型 | 选项来源 |
|---|---|---|
| 这条消息包含哪些意图 | 每个意图一道是非题 | 固定枚举 |
| 客人表达了哪些顾虑 | 每个已知顾虑一道是非题；新顾虑交给 `extract()` | 客人记忆里的顾虑，加上顾虑词表 |
| 客人选的是哪条线路或哪个日期 | 单选（含“没有选择”） | 本会话已展示的线路或团期，程序给出 |
| 这句回复确认了确认单的哪几项 | 每项一道是非题 | 确认单的项目 |
| 这个问题属于哪个主题 | 单选 | 问答簿主题枚举 |
| 下一步做什么 | 单选 | 程序本轮算出的允许动作 |
| 需求清晰度 | 每个维度 0–3 分 | 7.4 节的维度 |
| 草稿里有没有承诺性说法 | 是非题 | — |

**置信度的用法**：变更的“自动采纳”（7.3 节）额外要求判断置信度 ≥ 0.85；低于 0.6 时交给顾问确认，或转 `LLMDecisionBackend` 复核。阈值可配置，由评测集校准。

**不交给 Jev 的**：字段值的抽取（日期换算、人数、预算金额、地名）、所有要写出文字的内容。Jev 官方说明它不输出自由文本，也不擅长日期、计数和算术。

**切换条件**（P1 内完成对比）：
1. 在第 15 节的中文评测集上，各判断题的准确率不低于 `LLMDecisionBackend`；
2. 从 ECS（杭州）调用的实测 p95 时延；
3. 成本；
4. 合规评审：客人消息里有个人信息，发往境外服务前必须脱敏（姓名、证件号、电话替换为占位符）。

四项都满足才切换，并保留 `LLMDecisionBackend` 作为故障回退。

## 7. 需求状态与 Deal Engine

### 7.1 `DealState`

| 字段 | 类型 | 说明 |
|---|---|---|
| `destinations` / `destination_examples` / `regions` / `excluded` / `themes` | 列表 | 必去、举例、区域、排除（去过、不想去）、主题（极光、海岛、雪山） |
| `window` | 日期区间 | 可出发区间；“元旦前后”这类说法由程序的节假日表换算 |
| `days` | 区间 | “一周”这类说法按 ±1 天换算 |
| `depart_city` | 字符串 | 出发地 |
| `party` | 结构 | 成人数、儿童（年龄、是否占床）、老人（年龄）、总人数；程序校验总数一致 |
| `rooms` | 结构 | 房间总数和各房型分开记录；只知道总数时房型标为待确认 |
| `budget` | 结构 | 每人或总价上限、弹性（例如“老公定的，敏感”） |
| `preferences` | 列表 | 节奏慢、纯玩、不要红眼航班等 |
| `selected_route` / `selected_departure` | 引用 | 客人选定的线路和团期 |
| 每个字段附带 | 元数据 | `source`（原话、推断、顾问改、探索）、`evidence`、`version_set` |

- **版本账本**（`deal_state_version`）：保存每个版本的完整快照、变更集、采纳人和时间。对应原型的“需求演变 v1 → v2 → v3”。
- **来源优先级**：顾问改 > 原话 > 推断 > 探索。低优先级来源不能覆盖高优先级来源；遇到这种情况生成冲突，交给顾问决定（沿用现有 `conflicts` 机制）。

### 7.2 阶段与关口

| 阶段 | 进入条件（关口） | 允许的动作（枚举） |
|---|---|---|
| `explore` 模糊 | 清晰度低于找线门槛 | `ask_clarify`、`present_directions`、`note_memory` |
| `need` 需求 | 有时间和方向（目的地、区域或主题任一） | `search_routes`、`ask_clarify`、`answer_question`、`accept_changes` |
| `select` 选线 | 已展示候选 | `compare_routes`、`route_facts`、`build_plan`、`answer_question`、`search_routes`（仅需求变化后） |
| `date` 定团 | 客人选定线路（顾问点选，或 `decision.pick_route` 且顾问确认） | `list_departures`、`compare_dates`、`check_seats`、`answer_question` |
| `confirm` 确认 | 选定团期 | `build_confirmation`、`record_confirmation`、`add_note` |
| `quote` 报价 | 确认单全部确认 | `quote`、`share_quote`、`recheck_price` |
| `won` 成交 | 顾问登记定金 | `collect_documents`、`predeparture_task` |
| `hold` 占位（二期） | 报价有效 | 二期开放 |

每回合，程序根据状态算出允许动作，并按优先级规则排序，例如：有待采纳的变更 > 有未回答的问题 > 关口所缺的项 > 推进下一阶段。模型只在前 3 个里挑选，并给出理由。

### 7.3 变更与连锁影响

程序维护一张规则表。改动某个字段时，自动执行对应的影响：

| 改动的字段 | 程序自动执行 |
|---|---|
| 目的地、时间、天数、出发地 | 重新筛选候选；不再符合的候选标为“不符合 v(N+1)”；已选团期作废；已发方案页显示“调整中”；关口退回 `need` 或 `select` |
| 预算、偏好、主题 | 重新排序、重新生成匹配理由；不做硬过滤 |
| 人数、年龄、房间 | 报价作废，已分享的链接立即吊销（修复清单 N7）；检查年龄规则；确认单中受影响的项改为“待确认” |
| 客人选定的线路或团期 | 清空下游：团期、确认单、报价 |

**采纳规则**：
- **自动采纳**：`source=said`、没有冲突、不影响已发出内容的变更，比如首次录入。
- **需要顾问采纳**：其他所有变更，以变更单的形式出现（原型“需求变化”屏）。
- **无论哪种，都能撤销**：撤销即回到上一个版本。

### 7.4 清晰度与模糊需求策略

- **清晰度**：程序按权重打分，满分 100。时间 25、方向 25、人数构成 15、天数 10、出发地 10、预算 10、偏好 5。
- **找线门槛**：有时间，且有方向。

门槛未满足时，程序在两种策略之间选择：

| 条件 | 策略 | 说明 |
|---|---|---|
| 默认 | `ask_clarify` | 程序从缺失项里选出最多 2 个；模型把它们写成选择题，比如“寒假 / 春节 / 五一”“海边放松还是看欧洲” |
| 已经追问 2 次仍没有新信息，或客人表示“你推荐吧”（意图识别） | `present_directions` | 程序从目录里按“区域或主题 × 当季有团”聚合出 3 个方向，并给出真实的天数和价格区间；模型只写一句介绍 |

- 客人选了某个方向后，写入的字段一律标为 `source=explore`：只影响排序，不作硬条件，也不能说成“客人说过”。
- 三个方向都不选时，程序换一组，避开已经展示过的方向。

## 8. 客人记忆、问答簿与行程备注

**客人记忆**（`customer_memory`，跟着客人走，可以跨单使用）

| 分组 | 内容 | 来源 |
|---|---|---|
| 顾虑 | 标签、提到次数、每次的轮次引用 | `Understanding.concerns`，由程序累计 |
| 要避开的 | 去过的地方、不接受的安排 | 变更单中的 `excluded` 和偏好 |
| 我说过的话 | 顾问已发出的事实性承诺，附当时的 `fact_id` | 从 `ReplyDraft.claims` 中顾问实际发出的部分提取 |
| 沟通习惯 | 称呼、回复时间、谁拍板 | 模型函数 `backfill_memory()`，每 5 轮运行一次 |

- 智能体的上下文里只放整理后的记忆和最近 6 轮对话，不放完整聊天记录，从而消除 6000 字截断的问题（修复清单 N7）。
- **一致性检查**：线路内容更新后（route-kit 重新发布），程序比较“我说过的话”引用的事实是否还成立；不成立的生成“需要更正”提醒（原型“问答簿”屏）。

**问答簿**（`qa_entry`）
- 每个 `Question` 按线路和主题归档，保存最新回答、依据、问过的次数和轮次。
- 同一主题问到 3 次，程序标为“关键”，并开放 `make_explainer` 动作，用于生成一次讲清的材料。
- 没有依据的问题标为“待核实”，并开放 `ask_supplier`：生成一条问供应商的消息，顾问确认后发出。

**行程备注**（`itinerary_note`）挂在 route-kit 的行程节点上，格式为 `route_id / day / node_index`。按类型自动流转：

| 类型 | 自动去向 |
|---|---|
| 费用 | 报价单的“另付”项 |
| 特殊需求 | 订单备注，二期随占位或下单发给供应商 |
| 顾问备注 | 行前提醒草稿 |
| 客人问题 | 问答簿 |

## 9. 智能体设计

### 9.1 身份与职责

- **对话对象是顾问，不是客人。** 系统提示词第一句必须写明这一点（修复清单 N8）。
- **职责**：在本回合开放的工具范围内，把顾问需要看到的卡片组织好，比如候选线路、比较、团期、问答依据。
- **不负责**：决定流程阶段、修改状态、给客人写最终话术（第 6 步负责）、编造任何事实。

### 9.2 技能（按阶段加载）

技能是放在 `advisor/skills/<name>/SKILL.md` 的指令包，包含说明、输出要求和 1–2 个虚构示例。程序按阶段和意图，每回合加载 1–2 个。

| 技能 | 加载时机 | 要点 |
|---|---|---|
| `clarify` 模糊需求 | `explore` | 把缺失项写成选择题；不写成表单式的连环问 |
| `shortlist` 选线 | `need` → `select` | 用一两句话讲匹配和冲突；结果少时说明卡在哪个条件、放宽哪一项能多几条 |
| `compare` 比较 | 调用 `compare_routes` 时 | 按客人的顾虑逐条比较；先说贵的那条多了什么；好处和缺点并列 |
| `recommend` 推荐理由 | `build_plan` | 每条理由对应一个顾虑并注明依据；每份方案至少写一条缺点 |
| `answer` 答疑 | 意图为 `ask` | 只根据线路内容和政策回答；没有依据的标“待核实”；主动避免承诺性用语 |
| `negotiate_dates` 团期 | `date` | 并排比较两三个日期的价格、成团、返程、请假天数 |
| `confirm` 确认 | `confirm` | 逐项列出要核对的内容；从客人回复中判断哪些已确认 |
| `aftercare` 成交后 | `won` | 付款提醒、材料清单、行前提醒 |

技能文件以文本形式评审，改动走和 `system.md` 一样的派生与校验流程（`scripts/check.py`）。

### 9.3 工具

所有工具都是类型化的领域服务，返回结果带 `fact_id`，供回复引用。程序每回合只把“允许动作”对应的工具交给智能体。

| 工具 | 类型 | 作用 | 开放阶段 |
|---|---|---|---|
| `search_routes` | 只读 | 按 `DealState` 检索。硬条件由程序组装；模型只能传 `soft_terms`（主题词），影响排序（修复清单 N4）；返回漏斗计数和排除原因 | need、select |
| `route_facts` | 只读 | 读取 route-kit 线路内容的客户投影，可以按主题取 | select 之后 |
| `compare_routes` | 只读 | 2–3 条线路按顾虑和客观字段输出比较矩阵及差价拆分 | select |
| `present_directions` | 只读 | 按区域或主题聚合当季有团的方向和价格区间 | explore |
| `list_departures` / `compare_dates` / `check_seats` | 只读 | 团期、并排比较、实时余位 | date |
| `build_plan` | 写（方案草稿） | 生成方案及其版本号 | select |
| `build_confirmation` / `record_confirmation` | 写 | 生成确认单；记录客人确认（附原话） | confirm |
| `quote` / `share_quote` / `recheck_price` | 写 | 沿用现有报价和分享服务 | quote |
| `add_note` | 写 | 在行程节点上挂备注 | select 之后 |
| `ask_supplier` | 写（草稿） | 生成问供应商的消息，由顾问发出 | 任意 |

**已删除的工具**：`update_trip_brief` 不再由智能体调用，状态更新改由管线第 2、3 步完成；`present_suggestions` 由 `ReplyDraft.chips` 取代。

### 9.4 回复规范（由校验器执行）

- **给顾问的一句话**：结论加一个待办，不重复卡片上已有的内容。
- **给客人的草稿**：称呼用客人记忆里的称呼；每条事实都要有 `claims[].fact_id`；禁止出现“保证”“一定”“肯定能退”这类承诺，除非依据原文写明。
- **快捷回复**：只能是允许动作，或“客人可能会问”；引用的线路或团期编号必须是本会话展示过的（修复清单 N7 的正则问题一并解决）。
- **校验失败**：删除不合格的内容，并记录 `reply_violation` 指标。

## 10. 与 route-kit 的关系

答疑、比较、推荐理由、行程备注，都依赖**已复核的线路内容**。按 [`route-kit-integration-brief.md`](route-kit-integration-brief.md) 接入后：

- `route_facts` 读取客户投影，按节点和主题返回，每条附 `unit` 引用，这就是 `fact_id`。
- 线路内容重新发布后，触发 8 节的一致性检查。
- 没有已复核内容的线路，只能回答目录字段；其余问题一律“待核实”。

## 11. 数据与接口

**新增表**，全部带组织和用户外键、强制 RLS，写法沿用 `0038_trip_brief`：

| 表 | 用途 |
|---|---|
| `deal_state_version` | 版本快照、变更集、采纳人、时间 |
| `change_set` | 待采纳和已处理的变更单 |
| `customer_memory` | 客人记忆 |
| `qa_entry` | 问答簿 |
| `itinerary_note` | 行程备注 |
| `plan` / `plan_version` | 方案 |
| `confirmation` | 确认单项及确认记录 |
| `turn_trace` | 每回合各步骤的输入摘要、输出、耗时、校验结果，供回放和评测 |

**主要接口**：

- `POST /v1/deals/{id}/turns`：一回合，SSE 流式返回。
- `POST /v1/deals/{id}/changes/{cid}:accept|reject`：采纳或拒绝变更单。
- `POST /v1/deals/{id}/versions/{v}:revert`：撤销到指定版本。
- `GET /v1/deals/{id}/state|memory|qa|notes|plans|confirmation`：读取各项数据。
- 按钮动作：沿用 `POST /actions`，枚举与 7.2 节一致。

## 12. 模型与成本

| 调用 | 模型 | 预算 |
|---|---|---|
| `extract` | 快速模型（现有 DeepSeek Flash 配置） | ≤ 3s，≤ 2k 输出 token |
| `decide`（决策后端） | Jev 或同一大模型，按 6.1 节的对比结果选定 | Jev ≤ 1s；大模型 ≤ 3s |
| 智能体 | 同一配置，`max_tokens ≥ 4096` | ≤ 25s，最多 6 次工具调用 |
| `draft_reply` | 同上 | ≤ 5s |
| `backfill_memory` | 异步，每 5 轮一次 | 不阻塞回合 |

- **回合总时延目标**：p50 ≤ 12s，p95 ≤ 25s。
- **可配置**：模型通过配置项 `ADVISOR_MODEL_FAST` / `ADVISOR_MODEL_AGENT` 分别指定，不写死在代码里。

## 13. 安全与隐私

- **证件 OCR**：原图和识别结果单独存放在加密对象存储；证件号默认打码，访问记审计；出行结束 90 天后删除原图（保留期可配置）。
- **客户可见内容**：同业价、毛利、供应商名、余位数只出现在顾问端；方案页和报价链接沿用现有客户投影白名单。
- **不可信输入**：客人消息和线路内容都是不可信数据，在提示词里一律作为围栏内的数据（沿用 `fence_payload`），不能改变指令。

## 17. 风险

| 风险 | 对策 |
|---|---|
| 两次模型调用（理解、起草）加上智能体，时延变长 | 理解和起草用快速模型；按钮操作跳过理解；SSE 先推送理解结果，让顾问尽早看到进展 |
| 变更单太多，顾问嫌烦 | 7.3 节的自动采纳规则；批量“全部采纳” |
| Jev 刚发布，中文效果未公开，服务在境外 | 通过 `DecisionBackend` 隔离，可随时切回大模型；发送前脱敏；对比数据不达标就不切换 |
| 线路内容未复核，答疑能力弱 | 与 route-kit 接入并行推进；页面上明确标“待核实” |
| 节假日换算、年龄规则等业务规则不全 | 规则表由运营维护，改规则不改代码 |
