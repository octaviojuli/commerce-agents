# ADR-008：一次调用建立事务身份

状态：代码与隔离数据库验证通过；实际应用迁移记录见实施状态。

## 问题

每段业务事务原先需要两次数据库往返：设置用户/组织上下文，再检查有效成员。真实 HTTP 长负载下库存与报价接近但仍未达到延迟目标。需要减少固定往返成本，同时保留每段事务的实时身份、组织与行级权限检查。

## 决策

迁移 `0024_transaction_context` 增加 `public.warehouse_begin_context(uuid,uuid)`。`persistence.transaction` 在开始事务后调用一次该函数；函数顺序设置两个事务内配置值，再调用现有 `warehouse_has_org`，返回成员校验结果。不满足成员条件时，应用抛出 `Forbidden` 并回滚当前事务。

函数使用 `VOLATILE` 和 `SECURITY INVOKER`，以调用角色执行。只调用明确限定 schema 的 `pg_catalog.set_config` 与 `public.warehouse_has_org`；不使用函数级 `SET` 配置，身份上下文应保留到外层事务结束。SQL 参数绑定传入 UUID，函数不读取供应商凭据、不赋予组织成员身份、不缓存授权。

PUBLIC 执行权限被撤销，`grant_runtime` 仅为业务运行角色授予该函数执行权限。认证角色不需要执行权限。原有表 RLS、业务角色检查、供采授权检查、审批版本与事务提交边界保持生效。

## 生命周期与发布

正常提交或异常回滚都会清除事务内身份。拒绝成员后复用同一个连接也不得保留用户或组织；业务角色不能因为调用初始化函数而变成函数所有者。

迁移只新增函数，不修改业务表或数据。先安装迁移并授予运行角色执行权限，再重启加载新版应用与 Worker；旧应用仍可在迁移后继续使用原来的两条语句。回退代码后可保留这个未使用的函数；删除函数必须在所有调用它的进程停止以后进行。

实际应用升级前执行成套备份与校验，升级期间停止既有本地进程，核对迁移前后业务表摘要相同，再恢复 API 与 Worker。ECS 的独立部署验收仍须单独完成。

## 验证

- 初始化只发出一条应用 SQL，之后同一事务中可读到当前用户与组织。
- 执行角色仍是受限业务角色，函数不是 `SECURITY DEFINER`，认证角色无执行权限。
- 有效组织的其他用户、伪造组织和失效成员均被拒绝；提交、回滚、拒绝后连接身份被清除。
- 完整数据库回归覆盖组织隔离、实时撤销、报价、审批、库存并发、聊天和后台任务。
- 性能复测保留独立服务器进程、100 并发、原数据规模、原时延阈值和全部失败样本，结果见容量报告。
