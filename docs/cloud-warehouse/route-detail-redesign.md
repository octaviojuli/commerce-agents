# 线路内容工作台与客户展示设计

本轮为分析与交互草稿，未改动正式业务代码、云端配置或数据库。草稿为 `route-detail-redesign.html`，全部示例均为虚构 ACME 产品。业务约定更新为：同一供应源、同一团期和报价方案，所有采购客户使用统一同行结算价；日期、人数类别及方案仍可有不同价格。此前必须在商户详情逐一核验客户的交互不再作为目标方案。

## 当前问题的证据

| 用户问题 | 当前实现与实测 | 调整方向 |
|---|---|---|
| 进入详情会加载 | `business.tsx` 用 `useData` 在挂载后请求详情；旧组件随 URL 更换卸载，标题先显示“正在读取”。直接打开先恢复会话、读取组织，再读取详情；请求为 `no-store`，没有页面数据预取。 | 立即显示列表已有标题与基本资料，使用稳定骨架；已登录、同组织下按意图预取详情，并将读取、首屏和权限失败分别处理。 |
| 页面开头是标签吗 | 阳光西葡实时读取：`description` 为空，`features` 是字符串 `[]`，`tags` 为空数组，`itinerary_tags` 共 50 项。页面把 `features` 当正文，并将 `itineraryTags` 拼成“特色”长文本。 | 修正数组类型及空值；标签、卖点和产品简介各自展示，不再以原始标签拼成长段正文。 |
| 标签能用于顾问查询吗 | 云仓 `search.py` 目前只索引有效名称、上游名称、编号和出发地；现有这 50 项并未进入云仓顾问标签筛选。旧 Tour 直连 ERP 的标签逻辑不能代表云仓已实现。 | 已确认标签进入独立的筛选索引及顾问工具；未核实的上游自动提取标签只进入候选区。 |
| 简要与逐日行程是否保存 | `RouteDoc` 已有结构；解析稿写入 `document_parse.body`，审核发布写入 `document_publication.body`，都是数据库 JSONB。当前简要行程是读取 `days[].title` 拼出的目录，没有独立的每日简述。 | 保留结构化数据库，扩充每日简述和有类型的内容块；简要行程从同一每日记录派生，防止两套文字互相矛盾。 |
| 为何不完整、混乱 | 实际解析稿只有 2 个日条目、线路标称 13 天，部分标题为空；原文断行合并后留在 `days[].text`。新阅读样式无法修复旧的错误分日。 | 先改抽取和分日质量，再编辑提炼。不能只换排版，也不能让 AI 补齐没有证据的 11 天。 |
| 已有发布把关吗 | `documents._review` 已检查天数完整连续、每天标题正文及来源版本；2 天稿不能作为 13 天稿发布。当前商户详情允许有权限人员预览解析稿。 | 保留这些检查，增加用餐、住宿、票务矛盾检查与结构化问题定位；机器原文移入编辑对照区，C 端只读发布版本。 |

2026-09-25 公网浏览器的小样本：列表进入详情 91 / 448 / 412 ms，其中详情请求 48 / 49 / 36 ms；已登录直接进入详情 126 ms，组织和详情请求串行为 40 / 32 ms。这是当前测试链路的观察，包含浏览器自动化等待，不等于用户网络的固定体验或性能承诺。详情仅读数据库；代码确认本路径不触发 PDF 解析或 B2B 查询。还不能据此判断用户的一秒主要发生在网络、首次资源下载还是浏览器渲染。

## 内容分成四层

1. **原始证据**：API 原始 JSON、原始 PDF/DOCX/Excel、文件哈希、解析版本与实际页块位置。追加保存，不被润色覆盖。
2. **抽取候选**：按来源抽取每天、交通、景点、三餐、住宿和条款，保存候选值、来源与明确问题。规则或 AI 输出均为候选，缺失保留为空。
3. **编辑草稿**：商户可编辑的标准结构。允许整理句子、去噪、排序和归类；所有承诺性事实都能回到证据或人工补充记录。保留逐字段修订。
4. **已发布内容**：审批后创建不可变内容版本，客户接口按白名单投影。草稿修改、重解析与上游更新不会静默覆盖当前发布版本。

`原文 → 抽取候选 → 标准草稿 → 人工复核 → 发布版本 → 商户 / 顾问 / 客户各自投影`

数据库保存标准数据；页面只负责排版，不在打开时调用 AI 提炼。完整性分数只用于排序复核工作，不能代替发布条件或事实真实性。

## 字段设计

继续扩展现有 `RouteDoc`，采用版本化 `RouteContentV2` 契约。结构字段存于 JSONB，由服务端强类型校验；可筛选的基础属性和标签使用关系字段或可重建索引。没有必要为了每天的每一顿饭新建一套孤立表。

| 层级 | 建议字段 | 规则及用途 |
|---|---|---|
| 线路基础 | `product_id, route_code, title, subtitle, duration_days, nights, departure_places, destination_places, language` | 编号和所属供应源沿用产品主记录；来源事实与展示标题的覆盖关系继续明确。过夜晚数允许待核实，不能一律用天数减一。 |
| 产品简介 | `intro, highlights[]` | `intro` 为短介绍；每个卖点含稳定 ID、标题、说明和证据引用。与搜索标签分开，不用“全程四星”等未核实标签直接生成承诺。 |
| 标签 | `id, category, label, normalized_key, origin, source_ref, state, search_enabled, customer_visible, sort_order` | 分类至少有目的地、主题、交通、住宿、体验、适用人群。`state` 区分候选/确认/排除；同义词归一但保留原词，商户逐个增删改。 |
| 媒体 | `asset_id, kind, alt, caption, rights, customer_visible, sort_order` | 线路主图、图库及每日图片统一引用受控资源。不能把原始私有附件 URL 当客户图片。 |
| 每日主记录 | `day_id, day_number, title, route_places[], summary, blocks[], meals, accommodation, transport[], notices[], evidence_refs[]` | ID 稳定，排序与天数分开。`summary` 是复核后的 1–2 句简述；简要行程只引用这里，与详述同时失效、同时校验。 |
| 每日内容块 | `block_id, sequence, type, title, paragraphs[], place_ref, visit_mode, ticket_status, duration, time_window, media_ids[], evidence_refs[]` | `type` 为交通/游览/自由活动/购物/自费/提醒；`visit_mode` 为入内/外观/途经/待确认；门票是否包含独立表达，外观不等同“门票不含”。未给出时间不自动编造几点几分。 |
| 三餐 | `breakfast/lunch/dinner: {status, description, standard, evidence_refs[]}` | `status` 为已含/自理/不适用/待确认，不能空白即自理。三餐逐餐校验，而不只检查早餐。 |
| 住宿 | `type, city, names[], grade_text, grade_basis, or_similar, nights, evidence_refs[]` | 酒店/飞机/船上/火车/返家/待确认；星级来自官方评级还是供应商描述必须可区分。“或同级”保留原约定。 |
| 交通 | `mode, from_place, to_place, carrier, service_no, departure_local, arrival_local, timezone, arrival_day_offset, duration, distance, status, evidence_refs[]` | 参考与确定班次分开；跨日、时区和航班取消条件不可丢失。当前无结构的原文另存为 `raw_text`，不能乱推时间。 |
| 费用和条款 | `inclusions[], exclusions[], shopping[], optional_items[], booking_rules, cancellation_rules, notices[]` | 每条有类型、适用范围与证据。自费金额带币种、计费单位；线路规则与具体团期覆盖规则分开。重要条件不能被宣传摘要删掉。 |
| 质量和版本 | `schema_version, revision_id, parent_revision_id, source_content_hash, issues[], field_provenance, reviewed_by, reviewed_at, published_at` | 问题项含字段路径、严重程度、问题码和处理状态。来源页块不可随编辑改变；人工文字保留为人工来源，不伪造原文证据。 |

**来源与更新语义：** `source_content_hash` 针对相关内容与附件计算，而不是用每次同步的产品递增版本代表“内容已变化”。实际来源变更进入对照队列；纯库存/无关来源版本变化不应让全部行程反复提示内容过期。真实差异继续阻止错误审批。

**标签编辑语义：** API 原始标签留在来源快照。人工删除表示“本地排除”，人工修改保存原词与规范词关系；后续同步不把人工删掉的词悄悄加回来。新增来源词先作为候选。编辑并发布后，索引和已发布标签在同一业务版本下更新；投影落后时回退读取已发布标签，并继续实时检查可见权限。客户只看允许公开且确认的标签；顾问可筛选更多内部确认标签。

### 保存方式与原仓库衔接

- 保留 `supplier_product`、现有文档资产/解析/发布、审批、Outbox 和组织权限。
- 新增可持续保存的 `route_content_revision` 草稿：产品/组织/来源、父版本、基准发布 ID、来源哈希、结构正文及修订作者。并发使用期望版本；失效审批必须重新核对。
- 继续使用一个发布事实源。扩展现有 `document_publication` 以承载 V2 和草稿引用；为无文档的人工/Excel 内容增加受校验的来源类型。文档类型仍要求有效资产与解析关系，人工类型另记来源说明；不要建立另一个并列“正式行程表”造成双重权威。
- 独立的发布内容版本不再依赖每次目录同步。迁移须调整当前按产品版本唯一的约束、相关引用/授权与引用快照校验；旧 V1 发布保留可读，转换后生成草稿，不能自动审核发布。
- 公开接口专门构造客户字段白名单：内部采购价、客户查询身份、精确库存、人员/组织 ID、私有附件、原始 JSON、质量备注、解析工具信息全部不返回。只在页面隐藏不够。

## 解析、提炼与发布

1. 优先使用上游真正的结构化逐日接口；当前已核验适配器没有此接口，不能拿标签代替行程。附件进入已有异步 Worker，页面不等待解析。
2. 提取时保留页、表格、行列与原始段落边界，处理跨页续行；用标题、日序、表格和文档天数交叉判定，避免把天号、餐食或页眉归入错误的一天。低文本量、图片版、未知格式单独报错或进入后续 OCR 通道。
3. 安全去噪：页眉页脚、页码、重复宣传段等可标记排除；费用、购物、自费、签证、退改和限制条件不能因“让页面好看”被过滤掉。保留被排除项和理由供复核。
4. 规则先做类型、单位、空值、同义词与重复值整理；AI 如用于段落归类和摘要，只读选定证据，在严格 JSON 契约中生成候选。必须通过数值、实体、否定词及承诺范围对照；不能凭“可信度”自动填充缺项。
5. 商户工作台左侧选日，中间标准字段，右侧对应原文和缺项；可以按问题跳转修订。简述与详述共用来源，修改正文使相应简述待重新核对。
6. 发布硬条件：1 到 N 天连续、每天标题和正文、必要交通及住宿/餐食有明确状态、关键费用规则无未处理矛盾。未提供不是不存在；缺失的重要承诺必须补齐或在已审核文案中明确限制。媒体权限、客户投影、版本冲突都检查。
7. 审批创建不可变发布版本并更新搜索。原始附件重解析只产生新候选；发布失败保留旧版本，撤销发布立即关闭客户访问，不依赖缓存自然过期。

## 页面草稿

**商户维护**：固定线路标题、内容状态和预览按钮；页内分为概览与标签、逐日内容、费用规则、团期价格。标签使用胶囊，支持新增、编辑、移除，候选与生效内容分开；缺项不在阅读正文中大段铺开，而在问题面板定位。原文对照独立抽屉。保存草稿、校验、提交审核各有明确结果。

**客户预览**：主图/标题、简短卖点、公开标签、每日路线速览、逐日图文、三餐住宿、明确的购物/自费、费用与须知、可选团期及对客参考售价。显示可询/待确认，不显示精确余位或统一结算价。此次只规划浏览、选择团期和向顾问咨询；不扩大到自主下单、扣库存和支付。正式咨询应带线路发布版本、团期 ID 与用户明确提交的信息。

草稿支持标签增删改、每日摘要和段落编辑、问题定位、原文对照、保存和发布模拟、客户视角切换与移动端预览。模拟使用内存及本浏览器本地存储，退出草稿不改变 ECS；“客户预览”用于产品评审，不是可对外分享的生产页面。

## 统一结算价

界面直接按团期展示成人/儿童/老人/单房差的市场参考价和统一同行结算价，注明来源、币种、查询时间和刷新状态；移除客户编码输入、核验及选择步骤。“统一”针对采购客户，不合并不同团期、房型、人数类别或供应商的价。

技术路径优先使用上游标准结算价接口/明确字段。如当前 `/order/price` 仍硬性要求 `customerId`，由供应源管理员一次配置获确认的标准查询身份，服务端封装；这个参数不再作为本业务的差异定价维度，也不要求每个采购单位建立价格映射。采购组织和供采授权仍用于决定谁可看，不用于改变价格。

现有报价服务的客户映射前置条件也需要同步调整为“该来源采用统一价策略”，顾问、商户、缓存、报价快照及分享投影使用同一价格依据；不能只删界面而顾问报价继续被旧映射阻塞。保存 `pricing_policy_version`，查询缓存与快照绑定供应源、团期、方案、价表/策略版本及时间，不按采购客户区分。旧报价保持历史语义，不能回写成统一价；旧等级/协议价规则在采用统一策略的来源不参与选价，保留历史审计。

用户已确认阳光西葡的 12,700 元就是统一结算价；此金额作为该样本团期的业务验收基准。上游技术查询仍沿用获授权身份，但不再解释成该客户专属价格；需要实现后验证所有获授权采购组织均取得同一标准结果。这个样本金额不应硬编码成其他团期或其他线路的固定价格。草稿仍使用虚构示例金额。接口缺价、返回类型不符、过期或失败分别显示，不用市场价补入，不把零值当免费。

## 加载优化与验收

- 从列表进入：立即复用同组织、同产品、同版本的标题等已可见基本资料；正文异步到达填充骨架，避免整页闪烁。标题预填不是把未授权正文展示出来。
- 鼠标意图/键盘焦点预取详情，缓存限登录会话、组织、产品和内容版本；登出/切组织/403 时清除，保留实时权限复核。库存价格仍走独立新鲜度，不用内容缓存冒充实时。
- 首屏只取展示所需字段；原始全文、历史与附件按需加载。客户公开发布内容与员工私有草稿分开缓存策略，失效/撤销不能被长缓存绕过。
- 实测后设目标，而不是先承诺“零加载”。记录点击到标题、点击到首屏正文、详情请求耗时和失败率，覆盖首次打开、重复访问和手机网络。
- 验收至少包括：13 天稿误识别 2 天时拒绝发布；简述/详述及标签一致；标签人工排除跨同步不复活；内容变更才触发对照；两采购组织读取同一团期得到相同统一价；客户响应无结算价及余位数字；旧会话/报价按历史规则读取；所有模拟例不进入真实目录。
