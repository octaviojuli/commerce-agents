# ADR-005：API 线路展示补充与上游事实分离

## 需求与边界

供应商需要整理 API 线路的展示名称和介绍，采购方能够辨认内容来源。后续目录同步保留已审批补充，上游名称、原始快照、日期、价格、库存和已复核行程继续由各自服务负责。既有 Excel 内容编辑保持直接维护云仓所有的字段。

## 数据与读取

`supplier_product` 保留原始 `name`、`description`、`source`、`source_hash`；独立的 `name_override`、`description_override` 保存可选展示内容。`null` 表示沿用最新来源，空字符串介绍表示明确不展示介绍。展示名称不能留空。

`product_listing` 视图统一计算有效文字和逐字段 `source` / `warehouse_display` 来源标记，目录、商户、团期与报价复用此投影。采购搜索同时匹配源名称与展示名称。视图仅授予运行角色 SELECT，并使用 PostgreSQL 的 `security_invoker=true`，使底表的权限和行级策略以调用者身份执行；参见 [官方 CREATE VIEW 文档](https://www.postgresql.org/docs/16/sql-createview.html)。匿名查询、无授权采购方和授权撤销后的读取均由集成测试验证。

本方案延续规划中对开源电商“展示与业务资源分离”的借鉴，不引入新运行框架。采用同表独立列，避免一对一补充表额外的权限和连接路径；若扩展到多语言、多个销售渠道或平台与供应商多层文案，应迁移到有唯一作用域约束的独立覆盖表，不能继续无限添加列。

## 变更与版本

`product_display.py` 捕获源名称、源介绍、源摘要、供应连接版本、产品版本、展示版本和原覆盖值。产品编辑或供应商管理员提议；管理员核对源内容及前后差异后批准。应用锁定产品和连接、重新验证所有基准，与审计、Outbox 原子提交。旧页面提交、旧审批和伪造原值拒绝，重复应用返回既有结果。

展示变更只递增 `display_version`，保留产品事实版本。因此已发布行程和源附件不因名称整理而失效。报价记录展示版本，并在读取与发布时复核，使文案变化后的旧报价失效。审批账本保存完整原值、新值及来源基准，展示历史可从审批记录追溯；不把展示修改伪装成新的上游产品快照。

原 `MerchantBackend.stage_listing_update` 对 API 来源生成同一展示命令，对 Excel 来源继续使用原内容命令。对话只产生提议，工作台审批展示完整来源对照。恢复沿用通过专用展示表单完成，模型不能用空文字冒充撤销覆盖。

## 失效与交付

连接停用、组织或采购授权撤销仍以现有权限为准，补充不扩大可见范围。同步仅更新源字段，补充独立保留；上游变化不自动声明补充已重新审核。清除补充需要针对最新基准重新审批。

迁移只新增列和只读视图，不更改已有产品/团期/库存行的业务值。升级前备份并校验；升级后旧报价应重新核价。修改 API 展示文字不代表供应商确认了价格、库存或服务条款。生产试点仍需真实供应商及采购员工验收。
