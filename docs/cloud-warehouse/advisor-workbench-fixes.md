# 顾问工作台修复清单（移动优先版）

本清单针对 [`advisor-workbench-brief.md`](advisor-workbench-brief.md) 的现有实现，替代上一版清单。遵守 `AGENTS.md` 的约定，测试只用虚构的 ACME 数据。每一项单独提交，并附上对应的测试或截图。

## 0. 前提

顾问主要在手机上使用。运行环境依次是：微信内置浏览器打开的 H5、微信小程序的 `web-view` 内嵌 H5、手机浏览器。电脑宽屏仍然要能用，但属于次要场景。

本轮只做 H5，同时适配上面两种微信容器，不重写为原生小程序。以下要求都以 375×667 这一类小屏作为设计基准，再向上扩展到宽屏。

现有实现是先按桌面三栏设计，再在 780px 以下用"会话 / 对话 / 需求单"三个标签页切换。手机上存在这些问题：

- **对话区太小。** 标题栏、阶段条、标签栏加起来占去约 150px 高度，键盘弹起后对话区所剩无几。
- **看需求要切走。** 聊天时要看需求单，必须切换标签，离开对话。
- **输入框会触发缩放。** 输入框字号是 14px，iOS 在字号小于 16px 时聚焦会自动放大页面。
- **登录保不住。** 登录令牌存在 `sessionStorage` 里，微信里关掉页面后就要重新登录。
- **切出去就断流。** 顾问回微信和客人聊天时，页面切到后台，流式回答会中断。
- **复制容易失败。** 复制只依赖 `navigator.clipboard`，这个接口在微信内置浏览器里经常失败。

## M1【高】手机端改为"对话优先"的单屏结构

宽度小于 768px 时：

- **会话列表是单独一页。**
  - 列表每行显示客人标题和状态：待补需求、已选线、已报价、已发客人、待线下占位。
  - 列表顶部有"新客人"按钮和按客人标题搜索。
  - 点一行进入对话页；对话页左上角"←"返回列表。
  - 不再用标签页切换会话。
- **对话页从上到下依次是：**
  1. **顶栏**：返回按钮、客人标题、更多菜单（浏览目录、历史档案、退出登录）。
  2. **需求摘要条**，固定在顶栏下方：
     - 用一行横向可滑动的小标签显示关键字段，例如"4 人｜西葡｜1/28–2/16｜11–13 天｜上海"。
     - 同一行显示当前状态，例如"缺：房型"、"可询价·出行时间待确认"、"阶段：团期"。
     - 点一下，从底部弹出完整需求单和"当前选择"（线路、团期、报价状态）。
     - 桌面的阶段条在手机上不单独占一行，并入这条摘要。
  3. **对话区。**
  4. **快捷回复**（见 M2）。
  5. **输入框。**
- **高度预算**：在 375×667 下，对话区以上的所有固定元素，包括刘海和底部安全区，总高度不超过 112px。
- **失效提示在对话里也要出现**：报价失效时，除了摘要条要变色，对话里也要插入一条系统提示，并带"按新需求重新询价"按钮。
- **宽度 ≥1024px 时保留现有三栏布局**；768 到 1023px 之间用两栏：对话 + 需求单。
- **颜色一律用变量**：手机样式里写死的颜色（`#fff`、`#dfeef1` 等）改成 CSS 变量，深色模式下也要正常显示。

**验收**：在 375×667、390×844、360×780 三个尺寸下，截图覆盖以下状态，附在 PR 里：
- 需求录入后
- 检索结果
- 团期列表
- 报价
- 报价失效
- 发给客人
- 线下占位

另附一张键盘弹起时的截图，要求能看到最新一条消息和输入框。

## M2【高】快捷回复与卡片操作（原 F3，提升优先级）

手机上打字成本高，快捷回复是主要的操作方式。

**现状**：Shopping Agent 的 `present_suggestions` 输出的是字符串列表，而 `advisor_stages.public_suggestions` 只保留字典，所以快捷回复永远为空。

**要求**
- 保留字符串形式的建议，在服务端过滤：
  - 引用了 `WP-`、`WD-`、`WO-` 编号，但该编号不在 `seen_products` 里的，丢弃；
  - 指向当前阶段不允许的操作的，丢弃。用关键词映射到操作，写法参考 `examples/tour/api/next_steps.py` 的 `_legal_chips`。比如需求还不能询价时，含"询价""报价"的建议丢弃；还没有有效报价时，含"发给客人""分享"的建议丢弃。
- 删除只处理字典的死代码。
- 快捷回复显示在输入框上方，一行横向滚动，每个按钮高度不小于 44px，点击后作为顾问的一条消息发出。
- 卡片里的主操作（看团期、询价、发给客人）同样至少 44px 高，一张卡片只有一个主按钮，其余放进"更多"。

**测试**
- 在 `need` 阶段，"给 02-03 这团询价"被过滤掉，"2 大 2 小……"被保留；
- 引用了未展示编号的建议被过滤掉；
- 手机截图里能看到快捷回复。

## M3【高】团期列表按日期窗口排序，手机上用卡片列表（原 F1）

**现状**
- `advisor_actions.perform` 查询团期时传入 `include_out_of_window=True`。
- `advisor.py` 的 `_departures` 按 `ORDER BY d.id` 排序，团期编号是 UUID。

结果是第一页可能一个窗口内的团期都没有，顺序也近似随机。手机上一屏只能看到三四条，这个问题更明显。

**要求**
- 排序依次为：是否在窗口内（窗口内在前）、出发日期、编号。
- 分页游标改为按这个排序键翻页。游标里记录检索范围，范围变化时拒绝使用旧游标。写法参考 `advisor_matching.cursor`。
- 手机上每个团期是一行卡片，内容为：
  - 出发 → 返回日期；
  - 人数结论标签：有位、余位不足、待确认、窗口外；
  - 收客截止；
  - 一个主按钮"询价"。
  窗口外的团期折叠成"另有 N 个窗口外团期"，点开才显示。"加载更多"放在卡片内部，不经过聊天。
- 继续不展示具体余位。

**测试**：一条线路有 30 个团期，编号顺序和日期顺序故意打乱，窗口内有 3 个。断言：
- 第一页前 3 条就是窗口内的团期，并且按日期排序；
- 翻页后既不重复也不遗漏；
- 窗口变了之后，旧游标返回错误。

## M4【高】手机输入、键盘和需求单编辑

- **防止自动缩放**：所有 `input`、`textarea`、`select` 在手机上字号不小于 16px。
- **输入框始终在键盘上方**：
  - 视口 meta 加 `interactive-widget=resizes-content`；
  - 在不支持这个属性的环境（iOS、微信）里，用 `visualViewport` 监听高度变化来调整布局；
  - 底部留出 `env(safe-area-inset-bottom)`。
- **输入框自动增高**：最多 5 行，超出后框内滚动。支持粘贴客人发来的长段微信消息。
- **手机上回车换行，不直接发送**；发送只靠按钮。
- **需求单编辑放在底部弹层里**，尽量不需要打字：
  - 成人、儿童、老人、各类房间数用加减步进器；
  - 每个儿童的年龄用选择器；
  - 出行时间用日期区间选择；
  - 儿童占床用开关；
  - 偏好用多选标签。
  保存后，来源标签显示"顾问改"。

**验收**：在 iOS Safari 和微信内置浏览器（iOS、Android）实机上，聚焦输入框时页面不放大，输入框不被键盘遮挡，并截图。

## M5【高】微信容器兼容

- **登录保持**
  - 登录令牌改存 `localStorage`，读写都要包在 try/catch 里，失败时回退到内存；
  - 服务端采用滑动有效期，例如每次访问顺延，7 天没有使用就失效；
  - 服务端吊销后立即失效（现有行为保持）；
  - 退出登录时清除令牌；
  - 微信 openid 绑定登录不在本轮范围，只在 README 里记为后续项。
- **切后台、断网后恢复**
  - 页面在 `visibilitychange` 回到前台、或 `online` 恢复联网时，重新读取当前会话和需求单；
  - 如果本轮在服务端还是 `running`，每 2 秒轮询一次，直到完成，最长 90 秒，完成后显示完整回答；
  - 不要显示成"本轮已中断"的错误；只有服务端确实把这一轮记为中断时，才提示重新发起；
  - 流式回答在微信 X5 和 XWeb 内核里要实机验证。网关已经关闭了 SSE 缓冲，验证时确认这一点仍然有效。
- **复制**：客户链接和"复制给计调"的文本，依次尝试三种方式：
  1. `navigator.clipboard.writeText`；
  2. 隐藏 `textarea` 加 `document.execCommand("copy")`；
  3. 以上都失败时，把文本显示成可选中的块，并提示"长按复制"。
- **发给客人**
  - 手机上的主按钮是"复制发给客人"，复制内容为一句简短说明加链接，方便直接粘贴到微信。
  - 支持 `navigator.share` 时，另外提供"分享"按钮。
  - 在小程序 `web-view` 里不能直接调起转发，这一点写进 README。
- **客人打开的报价页**（`/p/[token]`、`/quote`）
  - 按手机优先重新检查：能在微信内置浏览器里正常打开，页面不横向滚动，字号不小于 15px；
  - 不含同行结算价（现有测试保持）。
- **部署前提写进 `cloud-warehouse/deploy/README.md`**
  - 小程序 `web-view` 只能加载已在小程序后台配置的业务域名。这个域名必须是 HTTPS、有有效证书、已完成 ICP 备案，并按要求放置校验文件。
  - 现在的 IP 加端口地址不能用于小程序。
  - 另外说明网关对 SSE 的要求。

**验收**：在微信开发者工具和一台真机上，用 `web-view` 各走一遍：登录 → 录入需求 → 询价 → 复制发给客人。然后把页面切到后台 30 秒再回来，回答应该完整显示。

## M6【中】模型不能覆盖顾问修改过的字段（原 F2）

**现状**：`trip_brief.patch(model=True)` 不检查字段原来的来源。顾问手动改过的字段，下一轮模型解析时可以直接改回去。

**要求**
- 模型写入一个来源为 `advisor` 的字段时，拒绝这次写入。
- 本轮其他字段照常写入，不要因为这一个字段让整批失败。
- 被拒绝的字段放在返回结果的 `conflicts` 里，内容包括字段名、顾问当前的值、模型提议的值。
- 前端在对话里显示一张冲突卡片，上面有两个按钮："保留当前值"和"改为：{新值}"。一次点击即可处理，点后者时走 PATCH。
- 在 `domain_search_notes` 里补一条短规则，说明遇到 `conflicts` 时怎么处理。改完后重新生成 `docs/cloud-warehouse/advisor/system.md`。

**测试**：顾问把"儿童占床"改成 `false` 之后，模型提交 `inferred: true`。断言：
- 该字段仍然是 `false`，来源仍然是 `advisor`；
- 同一批提交里的其他字段写入成功；
- 返回结果的 `conflicts` 里有这个字段；
- 前端点击"改为"后，字段更新，来源为"顾问改"。

## M7【中】检索结果在手机上的呈现

- 线路卡片单列排列。
- 匹配理由默认只显示一行摘要，例如"✓ 3 项符合 · ✕ 1 项冲突 · ? 1 项待确认"，点开再看逐项说明。
- 冲突项在摘要里直接写出名称，例如"✕ 北京出发"。
- 每轮最多展示 3 条线路，其余用"查看更多"按钮在卡片内加载。

## M8【低】完整度要提示推断项（原 F4）

只要 `readiness` 的 `inferred` 不为空，摘要条和需求单的完整度那一行就显示"可以询价·{字段名}待确认"，并用警告色。检索和询价两行分开判断。

## M9【低】客人举例的目的地不作为硬条件（原 F5）

**现状**：`advisor_actions.search_parameters` 把需求单里的所有目的地拼成一个检索词，而检索要求每个词都必须命中。

**要求**
- 需求单的目的地增加"必须覆盖 / 举例说明"的区分。一种做法是给每项加 `required: bool`；另一种是拆成 `destinations` 和 `destination_examples` 两个字段。
- 检索只把必须覆盖的目的地作为硬条件；举例的目的地只用来生成匹配理由（覆盖了、没覆盖、未知），并参与排序。
- 模型解析时，"等""比如""之类"这类说法记为举例。把这条写进 `update_trip_brief` 的工具描述。

**测试**：需求为"欧洲，举例德国、法国、意大利、瑞士"时，只覆盖其中两个国家的线路仍能被检索到，匹配理由里写明覆盖了哪几个国家、没覆盖哪几个。

## M10【中】弱网与首屏性能

- **首屏体积预算**：顾问首页首次加载的 JS 压缩后不超过 250 KB，把实测值写进 PR。
- **按需加载**：历史档案、线路目录、报价分享这些次要页面都改成按需加载。
- **不引入网页字体**。
- **加载占位**：会话列表、需求单、检索结果在加载时显示骨架占位。
- **慢网测试**：用 Chrome 的"Slow 4G"限速测一遍，记录首屏可交互的时间。

## M12【高】部署到 ECS，用真实云仓数据验收

**最终验收在 ECS 上完成，不以本地验收代替。** 部署前先读 [`ecs-acceptance.md`](ecs-acceptance.md)、[`recovery-runbook.md`](recovery-runbook.md) 和 `cloud-warehouse/deploy/README.md`，沿用其中已有的流程：
- 部署根目录 `/opt/tour-warehouse`，按 `releases/<标签>` 存放；
- 配置文件只放服务器上的私有目录；
- 镜像在 Linux 上构建，再做隔离容器验收；
- 顾问端公网入口为 `https://8.149.135.28/`。

### 部署前

1. **确认服务器当前状态。** 在 ECS 上读取当前的迁移版本和正在运行的镜像标签。文档里记录的版本有出入（`implementation-status.md` 写的是 `0032`，`mineru-skill.md` 写的是 `0034`），以服务器实际查到的为准。列出本次要执行的全部迁移。
2. **固定发布内容。** 从一个已提交的版本打标签发布，不从工作区直接打包。在发布说明里列出这个版本包含哪些改动。
   - 如果包含解析 Brief 的改动（例如 `0037_native_documents`、去掉 MinerU），同时要删掉 `document.env` 里的 MinerU 配置，并按那份 Brief 的要求做验收。
3. **先备份，再演练恢复。**
   - `0035` 到 `0038` 这几个迁移都不能降级，回退只能靠恢复备份。
   - 用 `warehouse backup`，把数据库和附件一起做一份一致性备份，并用 `verify-backup` 校验。
   - 在 ECS 之外的隔离空库上，用 `restore` 和 `verify-restore` 走一遍恢复，再在恢复出的库上执行本次的全部迁移，确认能成功。
4. **写回退步骤。** 旧镜像标签要保留。在发布说明里写明回退方法：切回旧镜像，并用上一步的备份恢复数据库。

### 部署

- 按现有流程依次完成：构建三个镜像、隔离容器验收（`scripts/container_smoke.py`）、执行迁移、执行运行角色授权、启动 API 和两个网页。
- 已有的 Worker 调度保持不变，不缩短供应商冷却时间。
- 顾问端要启用真实模型。模型凭据只放在 `api.env` 里，不进入代码、镜像、日志或提交。

### 用真实数据验收

- **账号**
  - 只用专门的验收顾问账号，放在内部采购测试组织下。不要读写真实员工的会话。
  - 账号初始密码按现有方式通过本地私有文件交付。
- **流程**
  - 用真实模型、真实云仓目录、真实 B2B 只读数据，按原型走完整流程：
    需求录入 → 检索 → 团期 → 询价 → 发给客人 → 线下占位。
  - 至少用 3 组不同的需求来跑，其中一组的目的地要用"举例"的说法，用来验证 M9。
  - 把对话的关键文字和截图写进验收记录。截图里不能出现令牌、客户链接密钥或同行结算价以外的敏感信息。
- **报价如实**
  - 真实报价可能因为客户映射未签认、来源费用不全等原因不完整。这时界面必须如实显示缺什么，不能为了通过验收去修改供应商数据或授权。
- **没有写操作**
  - 从 API 日志和上游请求统计核实：整个验收过程中没有向上游发出任何下单或占位请求；`inventory_pool` 和 `inventory_movement` 的内容没有变化。
- **对客页面**
  - 用真实报价生成对客链接。在手机上打开，核对页面不含同行结算价、余位数和供应商信息。
  - 验收结束后撤销验收用的对客链接。
- **性能**
  - 用手机网络经公网 HTTPS 访问，记录检索、团期、询价三类请求的耗时，给出 p50 和 p95。
  - 在弱网条件下记录首屏可交互时间。
- **部署后健康检查**
  - Prometheus 目标状态为 up；
  - 没有新增 5xx；
  - 两个网页登录返回 200，匿名请求返回 401，非成员组织请求返回 403；
  - 目录条数与部署前一致，没有重复。
- **微信实机**

## 通用验收

```bash
ruff check . && ruff format --check . && pytest && python scripts/check.py
python cloud-warehouse/scripts/ci_database.py      # 或用本地测试库跑 cloud-warehouse/tests，要求零跳过
cd examples && npm run build --workspace tour/storefront-web
```

**设备矩阵**：以下每种环境至少走一遍"需求 → 报价 → 发给客人"：

| 环境 | 尺寸或版本 |
|---|---|
| iOS Safari | 375×667、390×844 |
| Android Chrome | 360×780 |
| 微信内置浏览器 | iOS 和 Android |
| 小程序 `web-view` | 开发者工具和真机 |

浏览器仿真可以用于自动截图，但不能代替微信实机验证。PR 里分别列出哪些环境是实机验证的，哪些是仿真。

以上本地检查全部通过后，才进入 M12 的 ECS 部署。只有 M12 在 ECS 上用真实数据验收通过，才算完成。

本地 PostgreSQL 在 macOS 上启动时需要设置 `LC_ALL`，例如 `LC_ALL=en_US.UTF-8`，否则会报 "postmaster became multithreaded during startup"，数据库集成测试会被全部跳过。
