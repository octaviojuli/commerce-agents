# ADR-004：预留订单契约，保持一期交易关闭

**Status:** Accepted（一期预留方式）；二期交易实现及启用须另行确认。
**Date:** 2026-09-23
**Deciders:** 项目负责人已确认一期查询范围；开发实现遵循后端规划第 12 节。

## Context

云仓面向多家供应商和采购旅行社，库存分别由云仓或供应商系统管理。一期需要稳定的产品、团期、报价与销售流水标识，让二期订单能够关联已有事实；一期不创建顾问占位、订单或支付，也不收集履约客资。

现有 B2B 适配器的旧接口契约记录：创建订单已经包含上游预留，超额可能返回候补；部门来自切换后的 Token。该接口没有上游幂等键，也没有取消、释放或修改端点。新的云仓适配器只允许读取，不能因为底层旧客户端存在写方法而开启交易。依据见 [ERP 契约](../../examples/tour/docs/erp-contract.md) 和 `examples/tour/api/warehouse_connector.py`。

## Decision

在 `cloud_warehouse/order_contracts.py` 定义独立、冻结、拒绝额外字段的数据模型，并导出 [版本化契约包](order-contracts.json)。这些模型不注册 HTTP 请求、模型工具或 Worker，不创建数据库表，不实现状态转换，也不调用任何供应商。

| 契约 | 含义与边界 |
|---|---|
| `ReservationRequest` | 未来采购请求只有请求编号和报价编号；身份、供应商、客户映射、价格及消耗名额均由服务端解析 |
| `TransactionScope` | 固定采购组织、供应组织与连接，采购和供应组织不能相同；字段本身不是授权证明 |
| `ManagedInventory` / `SupplierInventory` | 判别联合只能选择一种库存权威；云仓绑定库存池，上游绑定外部团期及授权部门；名额数量必须有供应商规则版本，不按人数自动推算 |
| `OperationIdentity` | 本地去重作用域为采购组织、动作、资源及请求编号，另存规范化请求摘要；同键异内容未来须冲突 |
| `SupplierTransactionCapabilities` | 能力声明与执行开关分离；独立占位和“创建订单包含预留”分别表达，上游幂等需明确保证时长 |
| `ReservationSnapshot` | 占位事实及版本；有效占位必须有带时区的到期时间，上游已知状态保留可回查引用 |
| `OrderSnapshot` | 订单状态独立于占位；候补使用 `WAITLISTED`，不记已售；支付固定 `NOT_INTEGRATED`，本契约不包含资金结算 |
| `SupplierWriteResult` | 区分 `HELD`、`CONFIRMED`、`WAITLISTED`、`UNKNOWN`、`REJECTED`，未知结果的下一步只能是回查；不将超时当作明确失败 |
| `ReconciliationReport` | 记录观察时间、连接、部门和候选引用；唯一匹配、零匹配、多候选、无法查询分别表达，不因为零匹配就允许自动重发 |
| `ExistingSaleLink` | 引用已有订单、库存池及销售流水，额外已售量只能为零，防止一期销售记录在二期重复扣减 |

所有跨字段规则由 Python 模型校验。导出的 JSON Schema 描述字段、联合类型和基本约束；它不能独立证明跨字段一致性、数据库外键、组织权限或真实上游结果。二期接入方必须同时遵守本 ADR 和服务端校验。

## Options Considered

| 方案 | 复杂度 | 成本 | 扩展性 | 仓库适配 |
|---|---|---|---|---|
| 仅保留规划文字 | 低 | 低 | 字段与语义容易漂移 | 缺少代码校验和自动回归 |
| 类型契约、导出文件及关闭验证 | 低至中 | 无新增运行基础设施 | 能提前固定边界，二期仍需实现事务 | 沿用现有 Pydantic、pytest 和组织标识；采用 |
| 一期提前落订单表和交易状态机 | 高 | 增加迁移、恢复与维护成本 | 容易把未核实的供应商能力固化 | 超出已批准的一期范围；不采用 |

## Trade-off Analysis

借鉴 Medusa 将预留数量与库存实体分开记录的方式，用于约束“暂时保留”和“实际消耗”不能重复计数。Medusa 的通用零售履约流程不能直接替代旅游团期的确认、报名截止和供应商权威规则；这里没有引入 Medusa 依赖或复制其状态机。[Medusa Reservations Lifecycle](https://docs.medusajs.com/resources/commerce-modules/inventory/reservations-lifecycle)

冻结契约便于逐供应商审查，但不意味着二期所有字段永不变化。增加客资、支付、部分取消或拆分履约前，应增加独立契约或显式升级版本，不能把未验证数据放入任意 `metadata` 字段绕过当前白名单。

## Consequences

- 一期 `inventory_pool.held=0` 约束保持，报价和分享不扣库存。兼容 `/v1/holds`、`/v1/orders`、`/v1/payments` 继续拒绝；新的预留、订单创建及退款路由不注册。
- 契约没有 `apply`、`transition`、重试调度或交易适配器实现；模型构造成功不表示占位、下单或授权成功。
- 二期云仓占位的创建、确认、超时和释放，必须通过同一库存事务的条件更新处理竞态，并原子写入余额、流水、审计与 Outbox。当前文件不声称已实现这些保证。
- 二期上游写入必须先持久化尝试和幂等身份。请求可能已经送达但响应或提交丢失时，保存 `UNKNOWN`，按原连接与部门回查；无法唯一确认则人工处理。上游无幂等能力时不能把本地去重当作端到端防重复。
- 外部创建订单已包含预留时，不再扣云仓镜像库存。取消或释放也必须有实际供应商能力及确认结果，不能靠本地到期替供应商宣布释放。
- 关联一期已售流水前须验证组织、库存池、原始销售及冲正状态，并禁止重复关联。仅关联时 `additional_sold=0`；盘点纠错需走独立、明确审批的库存调整。
- `NOT_INTEGRATED` 不是未付款、付款失败或付款成功。收付款、授信、结算、发票和佣金继续在后续单独范围中。

## 商户已有订单读取

商户管理员可在已配置来源与部门范围内查询 B2B 已有订单。该能力由 `merchant_source_reads.py` 与连接器只读方法实现，保留上游状态、数量及金额，缺失值保持未知。它不采用二期 `OrderSnapshot`，不创建交易或库存流水，不建立历史订单的虚假报价关联。当前为实时读取，持久观察版本与后台订单同步尚未实现。
