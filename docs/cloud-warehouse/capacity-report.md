# 云仓容量验证

## 结论与边界

杭州 ECS 的规划容量尚未达标。授权函数计划复用后，隔离 1 核数据库的小规模四项目标已通过，报价 p95 为 394.82 ms；实际部署数据库仍限 1 核。隔离 2 核数据库的 100 并发、20,000 次 HTTP 长负载四项延迟全部未达标，请求零错误，库存与 5,001 份报价校验通过。小规模和此前本地通过的结果不能覆盖完整 Linux 容量验收。各轮失败与修复报告均保留。

原始报告：[优化前](capacity/baseline-before.json)、[目录优化后、连接池调整前](capacity/baseline-after.json)、[公平连接池延长基线](capacity/fifo-extended.json)、[异步入口修复后](capacity/async-extended.json)。结果包含失败样本与连接池等待，不剔除慢请求。测试库与角色均在结束后删除，并从集群侧核对只清理了本次资源。

## 服务层测量条件

- 本机 macOS arm64、10 个逻辑 CPU、Python 3.12.14、PostgreSQL 16.13；数据库连接上限 30，应用池最大 8。不是 ECS 性能数据。
- 50 家虚构供应商、100 家采购组织、10,000 条产品、100,000 条团期；一半供应商为托管库存，一半为 API 快照，50,000 个托管库存池与标准价表。
- 每个采购组织仅授权两个供应源，来源产品编号有重复。实际调用使用无超级用户、无 BYPASSRLS 的运行角色，核对返回供应商与团期范围。
- 短基线为 100 个线程并发提交 400 次混合调用；延长基线保持 100 并发，提交 20,000 次，每位采购方执行四类调用各 50 次。单请求计时包含等待数据库连接的时间，不含尚未进入并发线程的任务队列等待。
- 包含应用服务、RLS、报价解析及快照写入；不包含 HTTP、登录、浏览器、LLM、外部 API、网络延迟或专门的运营同步并发压测。最新延长基线执行约 51.60 秒，准备数据约 8.48 秒；本机现有业务进程仍运行。这不能替代长期负载与目标环境验收。
- 延长基线创建 5,001 份独立报价快照（含一份预热），不是重复读取已有幂等结果；所有托管库存仍为总量 100、已售/占位/冻结 0、版本 1。没有创建订单或调用上游系统。

## 已修复问题

1. 原搜索子查询在相同授权上下文重复扫描全目录。独立执行计划观测约 3,860 ms；直接使用当前产品检索副本及实时回退后约 247 ms。没有删掉实时回退或隐藏未建索引的产品。
2. 原产品/团期权限函数逐行重复读取供采关系。`0023_catalog_scope` 在每条语句计算当前采购方可读连接集合，仍检查双方身份、组织、来源、授权状态及有效期。结合直接匹配后，同规模独立目录执行计划约 4 ms。没有跨请求权限缓存，也没有把业务查询改为管理员身份。
3. 事务初始化合并两项本地上下文设置；成员校验仍在设置完成后执行。报价的候选价表、下一个生效时刻与采购等级改为同一条语句读取，候选集合只计算一次，保持整表优先级与所有 RLS 条件。
4. 分段诊断确认大量时间消耗在连接获取；同样最多 8 个连接，改用 Psycopg 直接向等待者归还连接，SQLAlchemy 不再叠加连接队列。延长基线验证四项服务层时延达标，没有扩大数据库权限或增加连接上限。

已有及新增回归覆盖实时撤销、伪造组织、连接复用、供应商非发布记录、源/展示版本落后、缺失检索副本、文字通配符、报价等级和有效期。加入连接池生命周期、故障、HTTP 超时恢复及事件循环/取消检查后，数据库套件 295 项通过、零跳过；时延阈值不作为任意负载 CI 机器上的确定性单元断言。

## TCP/HTTP 验证

`--transport http` 使用相同虚构数据规模、请求分配与阈值，在随机回环端口启动单事件循环 Uvicorn。100 个客户端线程与服务器处于同一 Python 进程，共享机器资源与 GIL；不等于独立压测机或 ECS 环境。测试数据库预置随机会话摘要，请求经过真实会话认证、组织校验、RLS、业务查询及 HTTP 序列化，未绕过权限。密码登录签发、TLS/反向代理、浏览器、模型及上游接口未包含在计时中。每次请求从客户端线程开始执行计时，包含连接等待、服务器队列与完整响应读取，不包含尚未进入客户端线程的提交队列。

启动检查验证匿名 401、伪造组织 403；请求检查可见供应商、团期集合、余位与价格，并核对 5,001 份独立报价和未变化的库存。失败响应按固定 HTTP 状态记录，网络异常只保存异常类型，原始响应、令牌和凭据不进入报告。测量异常后的监听关闭与数据库/角色清理有独立测试。

[初次短基线](capacity/http-baseline.json) 的 400 次请求无业务错误，但四项 p95 均未达标。[初次延长基线](capacity/http-extended-before.json) 完成 20,000 次调用，目录/团期/库存/报价 p95 分别为 942.58/941.75/950.73/980.65 ms；出现 4 次 `ReadError`，只生成 5,000 份报价快照而非预期 5,001 份，因此一致性计数与性能验收均未通过。失败样本和原始报告保留，不能用服务层通过覆盖此结果。

入口优化将会话、用户、成员和组织检查合并为认证角色的一条实时查询，移除重复的入口业务事务。各业务事务仍重新校验组织和行级权限，没有跨请求权限缓存；入口认证后撤销成员的请求被业务事务拒绝。纯令牌解析改为异步依赖，避免无数据库操作也排队占用工作线程。

[相同拓扑的优化后延长基线](capacity/http-extended-auth.json) 仍未达标：总耗时 90.10 秒，目录/团期/库存/报价 p95 为 882.08/864.16/879.75/901.51 ms。目录与团期各有一次 `ReadError`；5,001 份报价计数和库存不变检查通过，但不能因此忽略网络失败。优化前为 102.53 秒，比较仅限这两次本地同拓扑测量。

[分段短基线](capacity/http-timing-diagnostic.json) 在仅用于容量测试的 ASGI 包装层记录应用接收请求至响应头的时间；四类服务器 p95 为 246.33/253.66/247.97/515.74 ms，而客户端完整请求 p95 为 822.47/907.35/861.40/907.80 ms。不同分布的分位数不能直接相减来推算某段 p95，但差异说明仍须分析共享客户端连接池、同进程 CPU 竞争、应用开始之前及响应头之后的等待，不能全部归因于 SQL。后续需分别验证独立客户端连接和独立压测进程；现阶段没有解决连接读取错误，也没有放宽阈值或自动重试掩盖它。

## 独立服务进程与事务初始化

新增 `--http-server-mode process` 与 `--http-client-mode per-thread`，将 Uvicorn 放在独立子进程，每个负载线程使用自己的单连接客户端。默认保留原来的同进程、共享客户端模式，便于复现已有失败。子进程仅接收一次性本地测试库配置，通过继承的回环监听提供服务；正常退出、启动失败及子进程崩溃均检查监听与数据库/角色清理。客户端准备不计入单次请求时间，实际连接与完整响应读取仍计时。

改变测量拓扑后的结果不能直接算作后端优化收益。[独立进程长负载](capacity/http-process-extended.json) 完成 20,000 次请求，零错误，耗时 68.53 秒；目录/团期/库存/报价 p95 为 308.00/315.54/308.06/529.17 ms，库存和报价仍未达标。此结果也不证明旧拓扑或生产网络中的连接读取错误已经解决。

随后迁移 `0024_transaction_context` 将业务事务的身份设置与成员校验合并为一次数据库调用。函数保持调用者权限和事务局部上下文，不缓存授权；详见 [ADR-008](adr-008-transaction-context.md)。[同条件复测](capacity/http-context-extended.json) 耗时 66.83 秒，结果如下：

| 操作 | 请求数 | p95 | 目标 p95 | 错误 | 结论 |
|---|---:|---:|---:|---:|---|
| 授权目录搜索 | 5,000 | 300.91 ms | ≤800 ms | 0 | 本次达标 |
| 团期查询 | 5,000 | 308.08 ms | ≤800 ms | 0 | 本次达标 |
| 托管库存查询 | 5,000 | 300.04 ms | ≤300 ms | 0 | 未达标 |

两次长负载都创建 5,001 份独立报价，库存余额及版本不变，临时资源完整清理。未通过取整、重试或放宽阈值将结果判为通过。完整数据库及适配器套件 317 项通过、零跳过，包括四种 HTTP 拓扑组合、子进程崩溃、事务身份设置、实时成员拒绝及连接复用后身份清理。普通回归 1,785 项通过、235 项环境相关跳过。

## 剩余验收

原连接池对照实验中，16 连接未改善整体目标；32 连接配置超过本地数据库连接上限，出现连接错误，不能作为扩容方案。当前使用公平分配机制并保留最大 8 连接。隔离数据库的 ASGI 回归已验证慢查询不阻塞健康请求、SQL 线程归属与取消恢复；还需在目标环境验证 TCP/HTTP 长期混合负载、真实授权分布、同步 Worker 与文档解析共同运行。

还需覆盖商户筛选/排序、附件吞吐、外部报价预算、同步可见性、备份恢复容量及长期可靠性。5,000 行 Excel 的隔离 HTTP 样本验证见末节；真实文件和并发上传仍未验收。本报告不授权新购或升配资源。

## 响应验证调度对照

为区分编码与额外排队，使用相同 API 原文构造三个只读诊断版本：线上原逻辑、上一轮同步响应模型候选，以及异步接口加同一响应模型。异步候选只将原数据库调用整体放入 `run_in_threadpool`；数据库事务仍完整留在一个业务线程，身份依赖、字段与查询均保持原实现。代码仅在临时诊断目录中，不改运行服务。

[本地正反序六轮对照](capacity/response-dispatch-local.json)均使用 50 供应商、100 采购方、10,000 产品、100,000 团期、100 并发和 400 次请求。原版本总耗时 0.76/0.75 秒，同步响应模型 0.75/0.75 秒，异步候选 0.74/0.74 秒；托管库存 p95 分别为 160.93/153.85、189.76/183.09、150.39/153.78 ms。同步模型在该接口增加排队，整体差异很小，不能解释全部 ECS 退化或证明上线收益。六轮均无错误，报价数量及库存检查通过，临时数据库和角色清理完成。诊断包装初次缺少函数导出，在建库前失败，空结果不作为性能证据。

ECS 使用同一个 `20260924-13` 镜像，只读挂载上述 API 诊断模块，按“原版、同步、异步、异步、同步、原版”顺序执行相同 400 次请求。数据库仍为 2 核/1 GiB，客户端/API 合计 2 核/1.5 GiB；[执行记录](capacity/ecs-response-dispatch-execution.json)包含六轮资源与清理边界。
