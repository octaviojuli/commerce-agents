# commerce-agents

For agents working in this repo, commerce-builder plugin users included. The public
reference for commerce agents on Codex: a shopping agent and a merchant agent on three
paths each, five vertical examples, and a Codex plugin.

## Layout

- `cloud-warehouse/`: PostgreSQL-backed organization-scoped travel business services, supplier synchronization, migrations, and integration tests; `docs/cloud-warehouse/` holds its design and completion audit.
- `0036_platform_sales` adds an operator-enabled platform sales policy. Authorized advisors can read all active suppliers' published catalog without distribution grants; API quotes require the source's uniform price identity and Excel quotes select standard schedules only. `platform_sales.py` provisions independent advisors with private technical workspaces, without agency or supplier bindings. Quote snapshots and idempotency are actor-scoped; supplier originals, unpublished content and merchant writes remain private. `travel_search.py` splits destination terms and recognizes bounded aliases while retaining live catalog permissions. Upgrade with API and writers stopped, refresh runtime grants, then explicitly enable the policy; legacy distribution mode remains available for other deployments.
- Shared `route_doc.Source.page_locations` holds immutable physical PDF block locators. Tour `pdf_source.py` carries page evidence through line normalization; `route_parser.py` groups the selected extraction's original blocks. DOCX and old parses have no invented pages. Merchant document and approval views fetch private originals, clear preview object URLs on teardown or failed access rechecks, and distinguish source locations from human revisions.
- `0028_document_reparses` adds append-only parse generations per original asset. `documents.py` serializes explicit supplier reparse requests with publication, fences worker completion by generation and lease, preserves old published content, and rejects superseded draft approvals. Supplier-only history endpoints paginate immutable parses; reparsing never rebases a historical product snapshot or inherits a review. Migrate and refresh column grants with old API/document workers stopped before starting the new version.
- `cloud-warehouse/deploy/`: independent API/web images, optional database and scoped worker Compose services, private configuration templates and deployment procedure. Employee access goes through a public HTTPS gateway; database and API have no public host ports.
- Tour `warehouse_connector.connector_registry` binds connection UUIDs to operator-configured environment prefixes for both API and catalog CLI workers. Scoped workers load only their own secrets; missing/duplicate bindings fail before database or network access. Production Compose mounts the same registry for API and catalog workers; legacy standalone commands without a registry retain their explicit single-source configuration.
- `cloud-warehouse/scripts/ci_database.py` owns disposable PostgreSQL test databases and restricted roles, runs the warehouse and Tour connector suites with zero allowed skips, and cleans only resources it created. The `warehouse-postgres` CI job supplies the isolated cluster; the runner never loads application credentials.
- `cloud-warehouse/scripts/container_smoke.py` verifies prebuilt linux/amd64 API and both standalone web images on a dedicated Docker daemon with at least 4 GiB RAM. It creates a private network, fictional PostgreSQL identities and temporary object/config volumes, checks scoped HTTP reads, uploads, web proxies and API restart persistence, then removes only resources carrying its unique ownership label. `warehouse-images` builds and tests the images without application credentials or published host ports; local safety tests do not certify a Linux run.
- `cloud-warehouse/scripts/capacity.py` reuses that resource lifecycle for fictional, buyer-scoped service load probes. Reports include pool wait, failures, quote snapshot writes and inventory checks; they do not certify HTTP, upstream API or production capacity. `0023_catalog_scope` evaluates live buyer connection grants per statement without a permission cache.
- `cloud-warehouse/scripts/capacity_import.py` measures one fictional XLSX through a disposable HTTP process, restricted roles, preview, explicit fixture approval, publication and replay. It checks every inventory pool against its ledger and separates upload from standalone parser timing; a single-file result does not certify concurrent, public-gateway or real supplier acceptance.
- Capacity `--transport http` owns a real loopback Uvicorn listener, fixture-only opaque sessions and HTTP clients. Requests use the production authentication and business-role checks. Reports separate this same-process client/server topology from service probes; login issuance, TLS/proxy and external APIs are excluded. The listener stops and disposable roles/databases are cleaned on normal completion and measurement failures.
- `cloud-warehouse/scripts/capacity_http.py` owns the optional isolated Uvicorn process and fixture-only response timing. It accepts scoped test URLs through stdin and an inherited loopback socket, rejects application/remote database targets, and never reads application configuration. Capacity flags preserve the original thread/shared-pool topology for comparison; process/per-thread mode isolates the server interpreter and client pools while keeping workload and thresholds unchanged.
- Capacity `--http-server-processes` compares 1, 2, 4 or 8 isolated API processes on one inherited listener, dividing fixed aggregate runtime/auth pool budgets across them. Measurement waits for every child's readiness and records per-process request counts; startup failure, child death and measurement failure clean all children and disposable resources. It does not configure production workers.
- `cloud-warehouse/cloud_warehouse/database_pool.py` owns lazy Psycopg connection pools with FIFO handoff, health checks, bounded waits and queues. SQLAlchemy uses NullPool to avoid a second checkout queue. Engine disposal closes the owned pool; reuse opens a new pool. Engines are created inside each worker process, and tenant context remains transaction-local in `persistence.py`.
- `cloud-warehouse/cloud_warehouse/http_observation.py` supplies server-generated HTTP request IDs and structured completion logs. Pure ASGI observation covers complete responses, interrupted streams, cancellation and unhandled errors without logging URLs, headers, bodies or exception text. The API marks organization context only after successful authentication; the shared web proxy forwards response IDs. Serving entry points configure its private log sink and disable raw Uvicorn access logs.
- `cloud-warehouse/cloud_warehouse/http_metrics.py` owns an optional per-application Prometheus registry and operations-only `/metrics` credential. Counters and histograms use frozen route templates and bounded method/status/outcome labels, never organization or user IDs. Scrapes are excluded, streams finish only on completion/interruption, and deployment uses one worker per separately scraped API instance. Default metrics access is disabled; employee sessions and web proxies cannot expose the registry.
- `cloud-warehouse/deploy/prometheus.yml` and `warehouse-rules.yml` define bounded API scraping, recording rules and an internal scrape-failure alert. The optional Compose `observability` profile has a private monitoring network and separate persistent TSDB, without application secrets or external notification delivery. `scripts/local_monitoring.py` prepares private loopback configuration and runs a separately verified native binary; it preserves data across restarts. `warehouse-rules.test.yml` is validated by the fixed Prometheus version in CI.
- `cloud-warehouse/cloud_warehouse/concurrency.py` adapts synchronous business operations to async role protocols through the shared AnyIO worker pool. Complete transactions stay in one worker; supplier/model awaits stay on the event loop. HTTP chat cleanup shields lease interruption and agent closure from stream cancellation. A cancelled write response does not prove rollback; reuse its idempotency key or inspect the existing approval state.
- `cloud-warehouse/cloud_warehouse/jobs.py` owns durable per-source schedules, bounded retries, and worker leases; job completion and catalog publication share one transaction. Supplier Retry-After cooldowns persist in `sync_job.provider_not_before`; the database guard prevents human queue controls from shortening them. Workers do not approve human business changes.
- `cloud-warehouse/tests/test_worker_recovery.py` kills real fixture worker processes before and after catalog commit. It retains the default 60-second lease and checks rollback, natural-expiry takeover, stable identifiers, atomic audit/Outbox, and no duplicate publication after restart. It uses caller-owned disposable databases and reaps only its own children; it does not certify host or network recovery.
- `cloud-warehouse/cloud_warehouse/outbox.py` consumes events in bounded database-only transactions with per-consumer receipts, scoped serialization, retries and status. `search.py` owns rebuildable product search projections; source/display versions select the projection or live fallback, while product RLS always rechecks buyer visibility. Projection storage contains no prices, stock or private credentials.
- `cloud-warehouse/cloud_warehouse/operations.py` reports supplier-scoped synchronization, inventory ledger, attachment and search observations. Approved command failures record only fixed codes after the business transaction ends; database transport errors require state verification, not an assumed rollback. Merchant `operations.tsx` shares polling with sync controls and clears observations on organization changes. Unmonitored areas remain explicit; no external notifications or automatic repairs are performed.
- Catalog inventory freshness remains 300 seconds from observation. New sync jobs default to a 180-second delay after successful completion; startup never overwrites existing schedules. Operations estimates freshness headroom using both adjacent scan durations and polling margin, warning without extending snapshots or changing supplier configuration.
- `0024_transaction_context` supplies a SECURITY INVOKER function that sets transaction-local identity and checks live membership in one call. `persistence.transaction` rolls back denied contexts; commit/rollback clears them. The helper uses qualified function names and no function-local settings, has no PUBLIC or auth-role execution grant, and does not replace business RLS or role checks.
- `cloud-warehouse/cloud_warehouse/sync_management.py` owns scoped history pagination and versioned, audited supplier-admin controls. Issue details compare an allowlisted original observation with the latest successful batch in one statement, preserving missing observations and newer failed attempts without claiming repair. `examples/tour/merchant-web/components/sync.tsx` displays schedules, worker observations, manual queueing and full run/issue history; detail reads recheck scope on focus and every 30 seconds.
- `0027_departure_quarantine` adds source quarantine independent of local departure status and sales controls. Catalog publication withdraws previously valid departures when the source returns an unlinked route, including date-window moves; buyer RLS also hides their offers and quotes. Successful source repair clears quarantine with stable IDs and a new version. The migration repairs old publications from the latest successful source snapshot without inventing parents or inventory.
- `0029_quarantine_scope` preserves departure quarantine while restoring statement-scoped live buyer grants from `0023_catalog_scope`, including nested offer and inventory reads; it changes only read policies, without caching permissions or rewriting business records.
- `0030_pricing_scope` applies statement-scoped organization checks to connection and distribution reads and existing live catalog grants to price reads and the invoker-rights live-grant helper. Contract and grade targeting remain unchanged; no write policies or business facts change.
- `0031_authorization_plans` uses PL/pgSQL prepared execution plans for the existing organization, role, buyer-connection and live-grant functions. Every statement still reads live permissions; function rights, volatility, ACLs and transaction-local identity are preserved, without caching authorization results.
- `0032_source_cooldowns` and `source_limits.py` persist supplier-directed waits outside sync jobs. Registered Tour transport checks every HTTP attempt, including login, department switching and retries, under a live server-bound organization/connection context. Restricted functions only extend cooldowns; private tables have no runtime/auth grants. Offline grouping of connections for one upstream account preserves all existing deadlines and cannot reassign explicit bindings. This is reactive cooldown coordination, not an inferred supplier QPS/concurrency quota.
- `cloud-warehouse/cloud_warehouse/backup_jobs.py` serializes operator backup cycles with a private process lock, source-bound root, explicit space preflight and atomic last-success status. It never prunes archives; status checks the live lock and snapshot age without claiming a fresh restore verification. Optional systemd templates remain inactive until storage policy is configured. Recovery holds the existing shared object lock through snapshot export and object copy, excluding collection while allowing normal writers.
- `cloud-warehouse/cloud_warehouse/recovery.py` creates consistent PostgreSQL/private-object bundles and verifies empty-target restores against table hashes, object hashes, and the inventory ledger. Restored databases remain offline until operator activation; `docs/cloud-warehouse/recovery-runbook.md` describes the procedure and its limits.
- `cloud-warehouse/cloud_warehouse/object_gc.py` supplies offline-administrator local object inspection and explicit collection with a private durable journal. Every historical document_asset is retained; unknown names, symlinks and recent objects are skipped. Document writers hold a shared transaction advisory lock before writing bytes; collection takes its exclusive counterpart before reading references. Upgrade all writers and stop restore jobs before use; roots must never be shared between databases.
- `cloud-warehouse/cloud_warehouse/merchant.py` implements the original `MerchantBackend`; `merchant_commands.py` and `catalog_edits.py` use the shared persistent approval service, never the demo in-memory ledger. `pricing.py` and `quotes.py` own buyer-scoped prices and immutable quote snapshots; separate ID and organization/idempotency point lookups retain live RLS and snapshot version checks. `price_books.py` owns approved Excel price windows and connection-scoped buyer grades; selection uses one whole schedule, contract before grade before standard.
- External quote connector contexts share an eight-second asynchronous budget, including entry, reads and exit. Timeout snapshots carry no price; late results are discarded, caller cancellation propagates, and normal live authorization/version checks still precede persistence. This budget excludes surrounding database work and requires cancellation-cooperative adapters.
- `cloud-warehouse/cloud_warehouse/sales.py` owns supplier-approved local departure pauses and booking deadlines, shared by catalog, advisor, merchant and quote reads. It preserves upstream snapshots and stock; source conditions that have not been mapped remain unconfirmed. Merchant catalog and approval views provide the human workflow.
- `cloud-warehouse/cloud_warehouse/offers.py` owns approved Excel offer creation, descriptions and enablement. Offers share their departure's existing inventory pool; they do not create capacity. Merchant `offers.tsx` uses the approval center, and advisor queries require an explicit offer when multiple choices exist. API source offers remain adapter-owned.
- `cloud-warehouse/cloud_warehouse/product_display.py` owns approved API product display copy and reset-to-source actions. `product_listing` is a security-invoker read view with field provenance. Display versions invalidate quotes independently of source product/document versions. `product-display.tsx` shows source and effective content in the original merchant workbench; merchant agent edits use the same handler and approval ledger.
- `cloud-warehouse/cloud_warehouse/quote_shares.py` owns explicit quote-owner share capabilities, expiration, revocation and owner-scoped history pagination. Tokens persist only as hashes; the auth role resolves a scoped capability and runtime reads recheck live permissions. Customer projections exclude private prices and nested internal fields. Advisor `ShareQuote.tsx` and `CustomerQuote.tsx` provide preview and creation; `ShareHistory.tsx` shares filtered pagination and confirmed revocation between the quote panel and persistent management view. `/quote` reads anonymous market snapshots with a fragment token and a fixed POST path.
- `cloud-warehouse/cloud_warehouse/order_contracts.py` defines inactive phase-two request, scope, inventory-authority, snapshot, outcome and reconciliation contracts. It has no state transitions, persistence or supplier calls. `scripts/export_order_contracts.py` exports the review bundle under `docs/cloud-warehouse/`; ADR-004 and tests preserve disabled phase-one transactions, unknown-write reconciliation and zero additional stock deduction when linking prior sales.

Empty keyword searches omit the search projection join; keyword searches retain version-checked projection fallback.

## Design rules

- One model owns the conversation; a rule goes in a tool description, the prompt, or a skill by how often it applies.
- The static prompt and `tools[]` are the same bytes on every turn; per-request data goes in the fenced block after the breakpoint.
- UI is presentation tool calls, validated and filled in on the server, streamed as `ui` events.
- Third-party content is fenced data; writes are provenance-gated and capped in code; `checkout` charges nothing; merchant writes apply only through host approval.
- Core is domain-neutral; a vertical adds UI through `PresentationExtension` and keeps the rest to itself.
- Each mechanism is defined once, in `commerce_common` or a role core, and shared by all three paths.

## Fictional and original

No real company, brand, product, or person appears: the only company is ACME and its
lines; every brand, prompt, schema, and figure is invented here. Two exceptions:
deployment and integration targets (the README's "MCP connectors" section; platform and
SDK names in `docs/deployment.md`, the README's deploying section, and the platform tests),
and CC0 category photos listed in the `IMAGE-CREDITS.md` beside them. When in doubt,
redesign rather than rename.

## Conventions

- Python 3.11+, `ruff` (root `ruff.toml`), `pytest` (root `pytest.ini`), type hints, `pydantic` schemas; web apps are Next.js and TypeScript.
- Skill descriptions name the request class, without sample utterances; tool descriptions say when the tool applies; examples stay schematic.
- A change to prompt text, a tool description, a skill, or a fence notice re-derives `system.md`; `scripts/check.py` compares them.
- Prose: plain declarative sentences; one term per thing; each fact once, naming its module; each role in its own terms; a README says what a thing is, how to run it, and where its interfaces are; no history, dates, or process narrative; cut before restyling.
- A new module updates this file and its README.
